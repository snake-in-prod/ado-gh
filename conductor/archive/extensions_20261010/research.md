## Phase 1: Aliases — phase

### q2. How does GitHub CLI (cli/cli, current release) implement aliases: `$1..$n` substitution and appending unused args, `!` shell aliases and which shell, `gh alias set` validation (valid command check, reserved names, --clobber), `gh alias import` YAML format and validation, alias storage in config.yml, no recursive expansion. On Windows: running shell aliases with sh from Git for Windows vs pwsh/powershell, and how to safely pass positional arguments to PowerShell (quoting, $args).
**Answer:** gh v2.102.0 (latest release, checked via the GitHub API), read from source:

1. **Storage.** Flat string map under `aliases:` in config.yml (Get/Add/Delete/All). Default config ships `aliases: {co: pr checkout}`. A shell alias is the same string with a leading `!`. `set -` stores stdin byte for byte (trailing newline kept).

2. **Non-shell expansion (`expandAlias`, root/alias.go:81).** Loops over args; while the expansion still contains `$` it replaces literal `$<i+1>` with the arg; once no `$` is left, remaining args are appended. If `\$\d` remains it fails `not enough arguments for alias: <expansion>`. Only then `shlex.Split` + extra args. Quirks vs the spec's "unused args are appended":
   - (a) args are pasted into the text before splitting — an arg with spaces/quotes is re-split or breaks shlex unless the user wrote `"$1"`;
   - (b) while a `$` remains, args are silently dropped (`x $2` with `a b` loses `a`; a literal `$` in a jq filter drops every arg);
   - (c) `$1` also matches the start of `$10`;
   - (d) an arg containing `$` stops later appends; an arg containing `$2` can be re-substituted by a later arg, and one containing `$<digit>` can trigger "not enough arguments".

3. **Recursion.** Aliases are cobra commands (GroupID "alias", DisableFlagParsing); a non-shell alias's RunE re-executes root. Aliases are registered by ranging over a Go map (random order), each validated with `ValidAliasExpansionFunc` against the tree built so far. So alias→alias chaining works only when the target happened to be registered first (unreliable), and loops can never be registered (the target never exists yet). gh therefore avoids loops by accident. The spec's "expand once" is a deliberate difference; implement it by validating and dispatching expansions against built-ins only (and optionally extensions).

4. **Shell aliases.** `expandShellAlias` builds `[sh, -c, expansion[1:], --, args...]` (`--` only when there are args); no substitution by gh — `$0` is `--`, `$1`/`$2` are the args (confirmed locally). Exit code passed through via `ExternalCommandExitError`.
   - sh lookup: Unix `exec.LookPath("sh")`; Windows `safeexec.LookPath("sh")`, then `<dir of git>\..\bin\sh.exe`, then scoop `<dir of git>\..\apps\git\current\bin\sh.exe`, else "unable to locate sh … typically distributed with Git for Windows". gh never uses PowerShell.

5. **`gh alias set`.** Exactly 2 args, `-s/--shell` (adds `!`), `--clobber`.
   - Name check (`ValidAliasNameFunc`): shlex-split, `root.Find`; valid only if the found command is not runnable and exactly one word is left. Refuses built-ins, their cobra aliases, existing aliases and extensions (runnable); allows nested names like `'issue mine'`.
   - Invalid and not an existing alias → "already a gh command or extension"; existing alias without `--clobber` → "name already taken, use the --clobber flag"; with it → "Changed alias".
   - Expansion check: `!` always accepted; otherwise first word must resolve (`root.Find` ≠ root).
   - Effective order in gh is built-in > extension > alias (an alias clashing with an extension is refused). The spec's built-in > alias > extension with a warning is a difference to document.

6. **`gh alias import [<file>|-]`.** YAML must be a plain `map[string]string`; a parse error fails the whole import. Keys processed sorted; same checks as `set`, `--clobber` the same. Values stored as written (shell aliases need their own `!`). Skipped entries don't change exit code (0); the report goes to stderr on a TTY only. Missing filename with TTY stdin → "no filename passed and nothing on STDIN". The tree isn't updated during import, so entries can't point at each other.

7. **List and delete.** `gh alias list` (`ls`) prints importable YAML; with no aliases it returns a NoResultsError (exit 0, message on TTY only). No table/TSV/`--json`. `gh alias delete {<alias>|--all}` does not prompt; on a TTY prints "Deleted alias X; was Y".

8. **Windows and PowerShell.**
   - With `-Command <string>`, every later argument becomes command text, so positional args can't be passed. `-CommandWithArgs` (fills `$args`) exists only in pwsh 7.4+ (experimental 7.4, mainstream 7.5).
   - `-EncodedCommand` (base64 of UTF-16LE) works in pwsh and Windows PowerShell 5.1 and avoids command-line quoting problems. It expands the script ~2.7x against the 32767-char command-line limit (minor risk).
   - Recommended: `<pwsh|powershell> -NoProfile -NonInteractive -EncodedCommand b64("& { $1=$args[0]; $2=$args[1]; ...; <expansion> } 'a1' 'a2' ...; exit $LASTEXITCODE")`. **Assign by index** — a destructuring `$1,$2 = $args` gives the last variable the remaining array (with one variable, `$1 = $args` is an Object[]); add a one-arg test.
   - Each arg is a single-quoted literal with every single-quote character doubled: U+0027, U+2018, U+2019, U+201A, U+201B (PowerShell treats all as single quotes).
   - Verified locally with powershell.exe 5.1 (two args): `$1`/`$2` worked, an arg with a space and a literal `$x` arrived unchanged, exit code 7 came through.
   - Bind variables instead of text substitution: replacing `$1` in PowerShell text would break `-replace 'a(b)','$1'`.
   - Without `exit $LASTEXITCODE`, external exit codes other than 0/1 become 1.

9. **What ado has.** Inline `map[string]string` config can't load a nested `aliases:` map (config.go:30-33; inferred from yaml.v3 behaviour — not run by the skeptic). `HandleError` (pkg/cmdutil/errors.go:54, called at cmd/ado/main.go:26) can't pass through external exit codes. `google/shlex` and `cli/safeexec` are already indirect deps; Go's `exec.LookPath` already refuses current-dir binaries (ErrDot). `pkg/cmdutil/editor.go:60` already uses `sh -c '<cmd> "$@"' name args`.

## Phase 2: Extension Core — Dispatch and env contract / Help and completion

### q3. How does GitHub CLI dispatch extensions: lookup order vs built-ins and aliases, extensions found on PATH, env vars passed (GH_*), passing the -R repo, stdio inheritance and exit-code passthrough, running .exe/.cmd/.ps1/sh scripts on Windows, and showing extensions in help and shell completion (cobra dynamic commands vs ValidArgsFunction)? **Answer:** (unverified) The skeptic's corrections are applied below.

**How gh does it (v2.102.0)**
- **Lookup and order:** installed extensions come from one directory, `<dataDir>/extensions`, `gh-*` entries only; gh never searches PATH. Each becomes an eager cobra command (`Use: name`, `GroupID: "extension"`, `DisableFlagParsing: true`), skipped if `cmd.Find(name)` resolves to a core command. Aliases are registered **after** extensions and must pass `ValidAliasNameFunc`, which rejects any name resolving to a runnable command — so an alias named like an installed extension is silently not registered and `gh alias set` refuses it ("already a gh command or extension"). **gh's effective order is built-in > extension > alias.** ado's spec order (built-in > alias > extension) differs and belongs in docs/gh-differences.md; the implementation must register aliases before extensions (or skip extensions whose name is an alias) — a `cmd.Find` core-conflict check alone does not give alias precedence. `gh extension exec` reaches an extension shadowed by a built-in.
- **Environment:** `externalCmd.Env = append(externalCmd.Environ(), "GH_EXTENSION=1", "GH_PATH="+m.ghPath)`. No repo, host or TTY variables; gh has no global `-R`.
- **stdio and exit code:** `io.In/Out/ErrOut` are passed to `exec.Cmd`. These are `*os.File` except on Windows consoles without VT support, where gh's iostreams wraps Out/ErrOut in an `fdWriter` around `colorable.NewColorable`, so the child then gets a pipe. ado's `System()` passes real `*os.File` (iostreams.go:33-34), which is what ado should keep. `*exec.ExitError` is wrapped in `ExternalCommandExitError`; `Main` returns its code without printing. `gh help <ext>` becomes `gh <ext> --help`.
- **Windows:** binaries run directly; script extensions always via `sh -c 'command "$@"' -- <exe> args…`, with `findsh` (PATH `sh`, `<git dir>\..\bin\sh.exe`, scoop path) or "the `sh.exe` interpreter is required. Please install Git for Windows".
- **GH_PATH:** `GH_PATH` env if set; else `os.Executable()` and a symlink-aware PATH scan preferring the PATH entry, for the git credential helper gh persists in git config.

**Problems in ado the plan must handle**

## Phase 3: Install — Script install via git

### q5. Script extension install/upgrade via git: shallow clone vs full clone, checking out a pinned tag or commit, fast-forward upgrade to the remote default branch, passing an Authorization header for private Azure DevOps repos via GIT_CONFIG_COUNT/GIT_CONFIG_KEY_n/GIT_CONFIG_VALUE_n env (supported git versions), never via argv or persisted config; executable bit on Windows checkouts (core.fileMode), CRLF line endings breaking shebang scripts (.gitattributes), and how gh detects the executable in a script extension.
**Answer:**

1. **Full clone, not shallow (as gh).** gh: `git clone <url> <dir>`; pin → `git checkout <sha>` + `.pin-<sha>`; upgrade `git pull`, or `--force` → `git fetch origin HEAD` + `git reset --hard origin/HEAD`; update check compares `git rev-parse HEAD` with `git ls-remote origin HEAD`.
   - Shallow (`--depth` implies `--single-branch`) can handle tag pins via `--depth 1 --branch <tag>`, but not arbitrary commit SHAs, ancestry checks or later fast-forwards. Extension repos are small; full clone is simply simpler.
   - Install flow: (1) `git clone --quiet -c core.autocrlf=false -c core.eol=lf -- <url> <tmp-dir-inside-extensions-root>` (`--` stops a `-`-prefixed URL being an option); (2) if `--pin`: `git -c advice.detachedHead=false checkout --quiet <ref>`, then `git rev-parse <ref>^{commit}` to record the SHA (plus tag) in `.ado-install.yml`; (3) validate the executable, then rename the temp dir to `ado-<name>`.
   - Upgrade (pinned skipped unless `--force`): `--dry-run`/check compares `ls-remote origin HEAD` with `rev-parse HEAD`; upgrade = `git fetch origin HEAD` + `git merge --ff-only FETCH_HEAD` (follows a renamed default branch; fails cleanly on force-push); `--force` = `git reset --hard FETCH_HEAD`. This is better than gh's `origin/HEAD`, a clone-time symref that `fetch origin HEAD` doesn't repoint after a default-branch rename (note in gh-differences).

2. **Token for private Azure DevOps HTTPS clones.**
   - Env on the git process only: `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=http.https://<ado-host>/.extraheader` (URL-scoped), `GIT_CONFIG_VALUE_0=Authorization: Basic base64(":"+PAT)` or `Authorization: Bearer <token>` for Entra. Reuse the header logic in `api/http_client.go:118-124` (extract a small method). If the parent env already has `GIT_CONFIG_COUNT=n`, append at index n. Same env for `ls-remote`, `fetch`, `merge`; the remote URL stays clean, nothing lands in `.git/config`.
   - Never `git clone -c http.extraheader=...` (`clone --config` persists into the new repo) and never `git -c` (argv). `git --config-env=http.extraheader=VAR` is an alternative (also git 2.31; documented by Microsoft).
   - **Minimum git 2.31.0** (`GIT_CONFIG_COUNT` absent in 2.30.0 docs; 2.31 release notes: "Two new ways to feed configuration variable-value pairs via environment variables"). Older git ignores the vars silently → 401 or credential prompt. Check `git version` first (o14).
   - `GIT_TERMINAL_PROMPT=0` when not on a TTY. No token for `ssh.dev.azure.com` or github.com.
   - Redirects: `http.<url>.extraheader` scoping matches the configured remote URL; cross-host protection on redirect depends on curl stripping custom Authorization headers (git's `http.followRedirects=initial` limits following). Minor caveat.

3. **Executable bit on Windows.** clone/init probe the filesystem and set `core.fileMode` (false on NTFS; `os.Stat` shows no x bits). Check the git index on every OS: `git ls-files -s -- ado-<name>` must show `100755` (works with the stubbed runner too). Authors on Windows need `git add --chmod=+x` / `git update-index --chmod=+x`; gh's `extension create` runs `git add <name> --chmod=+x` itself. See o13.

4. **CRLF breaking shebangs.** Git for Windows installs with `core.autocrlf=true` (third-party source: Atlassian KB), i.e. `text=auto` + CRLF checkout → `#!/bin/sh\r`. `-c core.autocrlf=false` alone isn't enough: `core.eol` defaults to `native` (CRLF on Windows), so a repo with `.gitattributes` `* text=auto` and no `eol=lf` still gets CRLF. Forcing LF needs `-c core.eol=lf` as well; only the author's `ado-* text eol=lf` is fully reliable. Document `.gitattributes` `ado-* text eol=lf` (and `*.cmd text eol=crlf`). See o12.

5. **How gh finds the executable.** Only `<installDir>/<dirName>/<dirName>`. Install only checks existence (`hasScript` via the contents API for remote; `os.Stat` for local). On Windows non-binary extensions always run through Git for Windows `sh`; no `.ps1`/`.cmd`. The spec's preference is an ado addition (gh-differences).

## Phase 4: Binary Install and Upgrade — GitHub Releases binaries

### q6. GitHub Releases for binary extensions: REST endpoints for latest release and release by tag, asset listing and download (Accept: application/octet-stream), redirect to objects.githubusercontent.com / release-assets and dropping the Authorization header across hosts, goreleaser checksums.txt format (sha256  filename), asset naming conventions gh expects (gh-<name>-<os>-<arch>[.exe]), unauthenticated vs GH_TOKEN/GITHUB_TOKEN rate limits, and how gh handles prerelease/draft releases.
**Answer:** Checked against REST API 2022-11-28, a live probe on 2026-10-12, and gh trunk ec5b512.

**Endpoints**
- Latest: `GET https://api.github.com/repos/{owner}/{repo}/releases/latest` — "the most recent non-prerelease, non-draft release"; 404 when none (gh → `releaseNotFoundErr`).
- Pinned: `GET /repos/{owner}/{repo}/releases/tags/{tag}` — "Get a published release": a published prerelease tag resolves; a draft presumably 404s (inferred from the docs and gh's handling; status code not documented — medium confidence).
- Release JSON: `tag_name`, `prerelease`, `draft`, `assets[]` (`name`, `url`, `browser_download_url`, `size`, `state`, and since June 2025 `digest: "sha256:<hex>"`, not backfilled on old assets). gh reads only `tag_name` and `assets[].name/url`. `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2022-11-28` recommended.

**Download**
- `GET assets[].url` with `Accept: application/octet-stream`; "API clients should handle both a 200 or 302 response." The live probe got 302 → `https://release-assets.githubusercontent.com/github-production-release-asset/...?<signed query>` (older reports show `objects.githubusercontent.com`); don't hardcode the host. Counts against `core` rate limit.
- gh writes with `os.OpenFile(..., 0755)` (http.go:95).

**Dropping the token across hosts**
- Go's `http.Client` drops `Authorization` on redirects to non-matching domains. Use plain `f.HttpClient()` and set `Authorization: Bearer $GH_TOKEN` only when `req.URL.Host == "api.github.com"`.
- Do **not** use `api.NewHTTPClient`: its transport turns every 401 into `*cmdutil.AuthError` (api/http_client.go:172) → exit 4 + "run: ado auth login" (errors.go:74-77), wrong for a bad GH_TOKEN. The ADO credential never enters this client.
- Copy: `withoutURL` status-only errors (api/pipeline.go:296-318), query-stripping debug log (api/http_client.go:213-219), redirect test pattern (pkg/cmd/pipeline/shared/client_test.go:42-71).

**Tokens and rate limits**
- gh precedence: `GH_TOKEN`, then `GITHUB_TOKEN`, sent only to github.com / `*.ghe.com`.
- Unauthenticated 60/h per IP; PAT 5,000/h; Actions `GITHUB_TOKEN` 1,000/h per repo. Exceeded → 403 or 429 with `x-ratelimit-remaining: 0`; wait until `x-ratelimit-reset`. One install ≈ 3 core calls; an upgrade check 1 per extension. On 403/429 with remaining 0, hint to set `GH_TOKEN` (retrying doesn't help).

**checksums.txt**
- Lines `<64-hex>  <name>` (two spaces) — GoReleaser `fmt.Sprintf("%v  %v\n", sha, a.Name)` (checksums.go:217), same as `sha256sum`.
- GoReleaser's default file name is `{{ .ProjectName }}_{{ .Version }}_checksums.txt` unless `name_template` is set.
- gh-extension-precompile writes `checksums.txt` **only when GPG signing is configured** (`if [ -n "$GPG_FINGERPRINT" ]`, build_and_release.sh:91-95; README calls it optional), and its lines carry a `dist/` prefix. Most precompile-built gh extensions therefore have no checksums file at all (raises the weight of o16's digest fallback).
- Parser: split on whitespace, drop a leading `*`, compare basenames, skip blank lines.

**Asset naming as gh does it**
- gh picks the first asset whose name `HasSuffix(platform+ext)`, `platform = GOOS-GOARCH`, `.exe` on Windows (manager.go:296-306); no `gh-<name>-` prefix required. Precompile default asset names are `<os>-<arch>[.exe]` (`dist/${p}${ext}`, build_and_release.sh:75; uploaded basename). `isBinExtension` checks the latest release's assets against `possibleDists()`. darwin-arm64 falls back to darwin-amd64 under Rosetta; arm64 binaries are codesigned. No match → "`<repo>` unsupported for `<platform>`" plus an issue hint (no asset list — the spec's list is an ado addition). gh does **no** checksum verification.

**Prerelease and draft:** no prerelease flag; install and upgrade use `releases/latest`. `--pin <tag>` uses `releases/tags/<tag>` (prerelease works). Precompile marks any tag containing `-` as prerelease. Drafts are visible only to push-access users via the list endpoint.

### q8. GitHub repository search for extensions: `topic:ado-extension` query syntax, sort (stars, updated), per_page/limit, unauthenticated search rate limits (10/min) vs authenticated, fetching a repo README (raw vs API) for `browse`. Scaffolding for `ado extension create --precompiled=go`: how gh's `gh extension create --precompiled=go` lays out files and its release workflow (cli/gh-extension-precompile action), and an equivalent azure-pipelines.yml that cross-compiles Go for 6 os/arch targets, writes checksums.txt and publishes a universal package (UniversalPackages@0 task).
**Answer:**

**Search (`ado extension search`)**
- `GET https://api.github.com/search/repositories?q=<q>&sort=<s>&order=desc&per_page=<n>&page=<p>`; `q` = keywords + `topic:ado-extension` + `user:<owner>` per `--owner` (gh maps `--owner` to the User qualifier; `user:` matching orgs works in practice but is undocumented). Forks excluded unless `fork:true`.
- `sort`: `stars`, `forks`, `help-wanted-issues`, `updated` (default best match); spec allows `stars|updated` — validate and send only when set. gh sends `order` only with `--sort`; skip `--order`.
- `per_page` max 100 (default 30); at most 1,000 results per search. gh: `per_page = min(limit, 100)` + `Link` paging. Default `-L 30` is one request; cap `-L` at 1000.
- Fields: `full_name`, `description` (nullable), `stargazers_count`, `updated_at`, `html_url`, top-level `incomplete_results` → `--json fullName,description,stars,updatedAt,url`.
- Rate limits: search 10/min unauthenticated, 30/min authenticated; core 60/h vs 5,000/h. Exceeded → 403/429 with `x-ratelimit-remaining: 0`, `x-ratelimit-reset`, `x-ratelimit-resource`. Show reset time and a `GH_TOKEN`/`GITHUB_TOKEN` hint.
- `-w`: `https://github.com/search?q=<url-encoded q>&type=repositories`.

**Browse**
- gh's browse fetches `Limit: 1000` (10 search pages) and filters `gh-*` — unauthenticated that spends the whole 10/min budget. Recommend one page of 100 filtered to `ado-` (o22).
- README via API `GET /repos/{owner}/{repo}/readme` (preferred README, any name, default branch, optional `ref`), not raw.githubusercontent.com. Either `Accept: application/vnd.github.raw+json` and use the body, or gh's way: JSON `{name, content, html_url}` + `base64.StdEncoding` (ignores embedded newlines). Docs say raw+json is the default media type, yet gh base64-decodes with no Accept set — set Accept explicitly. 404 → placeholder. Cache READMEs in memory (gh uses a 24 h cached client).
- Reuse `markdown.Render(ios, md)` (pkg/markdown/markdown.go:36) and `cmdutil.OpenInBrowser` (pkg/cmdutil/browser.go:26). No new modules.

**gh's `create --precompiled=go`**
- Rejects values other than `go`/`other`; `git init --quiet <name>`.
- Go: writes `.github/workflows/release.yml`, `main.go`, `.gitignore` (`/<name>`, `/<name>.exe`), then `go mod init <host>/<user>/<name>` (needs `go` on PATH and an authenticated `CurrentLoginName`), `go mod tidy`, `go build`, `git add .`, commit "initial commit". Other: `release.yml` + 0755 `script/build.sh` with `git add --chmod=+x`. Script: `<name>/<name>` + `git add <name> --chmod=+x`. Next steps: `cd X; gh extension install .; gh N`, `go build && gh N`.
- Go `release.yml`: tags `v*`; permissions `contents: write`, `id-token: write`, `attestations: write`; `actions/checkout@v6`; `cli/gh-extension-precompile@v2` with `generate_attestations: true`, `go_version_file: go.mod`.

**gh's action vs our spec:** with its default build, `build_and_release.sh` builds 12 targets with `CGO_ENABLED=0 go build -trimpath -ldflags="-s -w"`, names outputs `dist/<os>-<arch>[.exe]` and writes `checksums.txt` only with GPG — not our `ado-<name>-<os>-<arch>[.exe]` + always-`checksums.txt`. It does have a `build_script_override` input (gh's own otherBinWorkflow.yml uses it); with it, the action runs the custom script and uploads every file in `dist/*`, so a script writing `dist/ado-<name>-<os>-<arch>[.exe]` and `dist/checksums.txt` would meet the spec. The plain-script workflow below is the simpler choice, not the only one:

```yaml
on: {push: {tags: ["v*"]}}
permissions: {contents: write}
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-go@v6
        with: {go-version-file: go.mod}
      - run: |
          for t in linux/amd64 linux/arm64 darwin/amd64 darwin/arm64 windows/amd64 windows/arm64; do
            os=${t%/*}; arch=${t#*/}; ext=; [ "$os" = windows ] && ext=.exe
            CGO_ENABLED=0 GOOS=$os GOARCH=$arch go build -trimpath -ldflags="-s -w" -o "dist/ado-NAME-$os-$arch$ext"
          done
          cd dist && sha256sum * > checksums.txt
      - run: gh release create "$GITHUB_REF_NAME" dist/* --generate-notes $([[ "$GITHUB_REF_NAME" == *-* ]] && echo --prerelease)
        env: {GH_TOKEN: "${{ github.token }}"}
```

## All phases — risks

### q9. Security risks and mitigations: path traversal / zip-slip in release archives and universal packages, symlinks inside the extensions dir, the `extension_sources` allowlist matching rules (normalize host/owner/repo, case, URL forms, ssh vs https, visualstudio.com), token consent bypasses (extension re-reading the keychain/config, ado auth token speed bump limits), tokens in process lists/logs/env of child processes (ArtifactTool, git), TOCTOU between checksum verification and install (verify the exact file that is installed), and lessons from gh security advisories about extensions.
**Answer:** Most hardening already exists; the work is reusing it and closing a handful of gaps.

**1. Zip-slip and path traversal**
- Release assets are raw binaries; nothing is extracted. Never use a server/manifest-supplied name as a path: destination is always `ado-<name>[.exe]` built by ado; look up `checksums.txt` entries by exact string; build API URLs with `url.PathEscape` for owner/repo/tag (gh GHSA-4fjg-2h4q-fwg3).
- The ArtifactTool zip does need extraction (az uses `zipfile.extractall`, no hash). Reuse `shared.ExtractZip` (LocalPath check before writing, `os.Root`, symlinks skipped, size capped) after moving it to a neutral package.
- Universal package output: fresh `os.MkdirTemp` as `--path`, opened with `os.Root`; accept only the exact expected binary name and `checksums.txt`, `Lstat` must show a regular file.
- One strict extension-name check (e.g. `[a-z0-9][a-z0-9._-]*`, never `.`/`..`) shared by install/remove/exec/upgrade; refuse a manifest `name` differing from the repo-derived name. ADO repo names allow characters GitHub's don't, and `adocontext.validSegment` (remote.go:84-88) doesn't reject `.`/`..`; gh's `Remove` does `RemoveAll(filepath.Join(installDir, name))` on a barely normalised name. `SafeName`/`LocalPath` (output.go:15-29, 59-71) cover Windows device names.

**2. Symlinks in the extensions dir**
- gh GHSA-39wj-f2f4-978v (fixed v2.102.0): writes outside destinations via symlinks; fix = hold the destination dir open, write relative to it, create files exclusively. Do every write through `os.Root` with `O_EXCL` (`shared.CreateFile`, output.go:44-57). `os.Root` follows symlinks only within the root.
- Local installs: `remove` removes only the link/pointer (`os.Remove`, not `RemoveAll` on the target); list/dispatch use `Lstat`; never write `.ado-install.yml` through the symlink.
- Script clones: no `--recurse-submodules`; `GIT_ALLOW_PROTOCOL=https:ssh`, `GIT_PROTOCOL_FROM_USER=0`; clone URL built from parsed parts with `--` before it; reject `--pin` values starting with `-` (gh GHSA-qcwj-mr2r-2cx7 argument injection). Same for ArtifactTool args from the manifest (feed, package, version): validate charset, refuse leading `-`.

**3. `extension_sources` allowlist**
- Canonical lowercase forms: `github.com/<owner>/<repo>`; `dev.azure.com/<org>/<project>/<repo>` (map `{org}.visualstudio.com[/DefaultCollection]`, `ssh.dev.azure.com:v3/…`, `vs-ssh.visualstudio.com`); `local`.
- For ADO, reuse `adocontext.ParseRemoteURL` (remote.go:42-68): rejects `\ ? #` and control chars, https:443/ssh:22 only, unescapes once, drops userinfo and `_full`/`_optimized`, resolves ssh aliases via `ssh -G`. It returns `errNotADO` for github.com and its HTTPS form requires `_git`, so GitHub sources (`owner/repo`, URLs, `git@github.com:`) need separate parsing. Add `.`/`..` rejection and strip trailing `.git`.
- Compare `url.Parse` hosts, never string prefixes (`https://dev.azure.com@evil.com/` → host evil.com). Malformed pattern (`path.ErrBadPattern`) or unreadable config → refuse (fail closed). Re-check on upgrade from the recorded source.
- Bypasses: (a) GitHub redirects transferred/renamed repos — also match the API's `full_name`; (b) `binaries.azure-artifacts.organization` can name a non-allowlisted org — check it too or require it to equal the source org (o25).
- With `path.Match`, `dev.azure.com/myorg/*` doesn't match a 3-segment ADO path; matching rule per o24.

**4. Token consent bypasses** (consent is a convention, as the spec says): an extension can unset `ADO_EXTENSION_NAME` and call `ado auth token`; call `$ADO_EXECUTABLE api …` (stored token, `Store.Token` env → keyring → config, store.go:56-77); read the keychain directly (go-keyring uses `/usr/bin/security` on macOS, Secret Service on Linux); read the 0600 plaintext fallback in config.yml (config.go:128-151); ask Git Credential Manager. Two real gaps:
- (i) inherited `ADO_TOKEN`/`AZURE_DEVOPS_EXT_PAT` (store.go:20) reach non-consented children built from `os.Environ()` — strip them (o2);
- (ii) for script extensions, `.ado-install.yml` inside the extension dir is in the attacker's work tree: the repo can ship one with `tokenConsent: true` or bring one in on `git pull`, and an ado-written untracked record makes `git pull` fail ("untracked file would be overwritten"). Keep records outside the clone or refuse repos that track the path (o10).
- Speed bump: top of `token.go` RunE (token.go:25-35).

**5. Tokens in process lists, logs and child env**
- Logs: the shared transport redacts `Authorization` and drops query strings in `--debug` (api/http_client.go:214-226). `IsADOHost` (pkg/cmd/auth/shared/http_client.go:13-24, 45-50) and the `ado api` host check (api.go:367) keep the ADO token off non-ADO hosts.
- GitHub client: its own host check so `GH_TOKEN` goes only to api.github.com — a transport setting `Authorization` per request in `RoundTrip` defeats Go's redirect stripping (gh GHSA-jwcm-9g39-pmcw / CVE-2024-53858 submodule token leak; GHSA-8xvp-7hj6-mcj9 / CVE-2026-48501 tokens to TUF/sigstore hosts, fixed 2.93.0).
- Git: add an env hook to `internal/git.Client` (git.go:51-57, 66-99); URL-scoped `http.https://dev.azure.com/<org>/.extraHeader` via `GIT_CONFIG_*`; `GIT_TERMINAL_PROMPT=0`. git's docs: argv may be readable by other processes (`/proc/self/cmdline`), environ is not (Linux default).
- ArtifactTool: `--patvar <VARNAME>` with the PAT in that variable (as az). Download the ArtifactTool zip with plain `f.HttpClient()` — don't rely on `IsADOHost` excluding the `uri` host, which is unverified. Cache in the 0700 data dir; no hash to verify it against (residual risk; az doesn't verify either).
- Windows `.cmd` extensions: Go's os/exec doesn't escape args for `.bat`/`.cmd` (golang/go#69939, open) — document or prefer `.ps1`/`.exe`.
- PowerShell aliases: escape all five single-quote characters.

**6. TOCTOU — verify the bytes you install**
- Stream download (or the copy out of ArtifactTool's output) into an `O_EXCL` temp file in a staging dir (`os.MkdirTemp` under the extensions root), hashing via `io.MultiWriter(file, sha256)`; compare with `checksums.txt`; set mode through the open handle (`f.Chmod(0o755)`; `Root.Chmod` races on Unix); close, write the record, rename the staging dir into place (`Root.Rename` since go1.25; go.mod 1.25.8). Never reopen by name between hashing and install. Existing `CreateTemp`+rename pattern: config.go:139-151, msal_cache.go:186-198.
- Windows upgrade: Windows lets you rename a running `.exe` but not overwrite/delete it; renaming the whole extension directory can fail while any file in it is open. Rename just the binary aside (as gh) or treat a failed rename as "close the extension and retry".
- Limit: `checksums.txt` from the same release proves integrity, not authenticity (signing out of scope). gh verifies no checksums at all.

- Setting `ADO_REPO` for extensions switches off git-based behaviour in nested `$ADO_EXECUTABLE` calls and forces `dev.azure.com` even for `*.visualstudio.com` clones — factory.go:46-47, resolve.go:23-24 (q3)
- cobra cannot tell `-R` before the extension name from `-R` after it under `DisableFlagParsing`; needs a raw-argv pre-scan — cobra command.go:714-745, 1869-1871 (q1, q3)
- Duplicate cobra command names resolve nondeterministically (first match + unstable sort) — cobra command.go:798-803, 1332-1338 (q3)
- A hand-written nested `aliases:` / `extension_sources:` in config.yml fails to load today (inline string map) — config.go:30-33 (q1, q2; failure inferred from yaml.v3, not run)
- Script extension directories are attacker-controlled git work trees; an `.ado-install.yml` inside can be shipped or pulled with `tokenConsent: true`, and an untracked record breaks `git pull` — spec FR4 (q9)
- Local-install records can't live inside a symlinked or pointer-file entry without polluting the author's tree — spec FR4, gh symlink_windows.go (q4)
- Windows CI runs as admin with UAC off: symlinks succeed, `.ps1` execution policy differs from client defaults, pwsh 7 is always present — the symlink fallback, Restricted policy and `powershell.exe` 5.1 fallback are never exercised by CI — GitHub runners docs (q4, q10)

- Go os/exec does not quote arguments for `.cmd`/`.bat`; args with `&|"%` can be mangled or injected — golang/go#69939 (q3, q9, q10)
- git < 2.31 silently ignores `GIT_CONFIG_COUNT`, giving a confusing 401 or credential prompt for private ADO script extensions — git 2.31.0 release notes (q5)
- `core.autocrlf=false` alone does not force LF; `core.eol=native` plus a repo `* text=auto` still yields CRLF shebangs on Windows — git-config core docs (q5)

- ArtifactTool: osName spelling and server case-sensitivity unverified; arm64 availability unclear; `uri` host and pre-signing inferred; exit codes and stderr format undocumented; no integrity hash; no published license terms — az CLI and Pipelines task sources (q7, q9)

- Universal Packages exist only in Azure DevOps Services, not Server — Microsoft Learn (q7, q8)

## Decisions
- o1: How should `extension_sources` be stored and edited? → YAML list in config.yml, plus `ado config get/set extension_sources` support using a comma-separated value (user, 2026-10-12)
- o2: Should ado strip `ADO_TOKEN` and `AZURE_DEVOPS_EXT_PAT` from the environment of extensions without token consent? → Strip `ADO_TOKEN` and `AZURE_DEVOPS_EXT_PAT` from extensions without token consent, and warn once on stderr when a token was withheld (user, 2026-10-12)
- o3: When the user is signed in with Entra ID, what should `ADO_TOKEN` carry for a consenting extension, given nested `ado` sends env tokens as Basic? → Pass the Entra token plus `ADO_TOKEN_TYPE=bearer`, which the child ado honours (user, 2026-10-12)
- o4: Should `$1..$n` expansion follow the spec's per-token rule or copy gh's algorithm exactly? → Spec rule: split first, substitute per token, append every unused arg (user, 2026-10-12)
- o5: Should `ado alias list` print YAML when piped (gh parity, round-trips into `alias import`)? → YAML when piped (gh parity), table on a TTY, plus `--json` (changes spec FR1) (user, 2026-10-12)
- o6: Should nested alias names like `ado alias set 'pr mine' 'pr list -a @me'` be supported? → No, top-level alias names only (user, 2026-10-12)
- o7: What should `ADO_REPO` contain when the repo came from git remotes rather than `-R` or an inherited `ADO_REPO`? → Set `ADO_REPO` only when `-R` or an inherited `ADO_REPO` was given; otherwise export `ADO_HOST`/`ADO_ORG`/`ADO_PROJECT` plus a new `ADO_REPO_NAME` (changes spec FR3) (user, 2026-10-12)
- o8: Should `.ps1` extensions run with `-ExecutionPolicy Bypass`? → Yes: `.ps1` extensions run with `-NoProfile -ExecutionPolicy Bypass -File`; Group Policy still wins (user, 2026-10-12)
- o9: Should PATH-only `ado-<name>` executables appear in `ado --help` and completion? → Yes, PATH extensions appear in help and completion, scanned lazily only inside the help func and the completion function (user, 2026-10-12)
- o10: Where do install records (`.ado-install.yml` with `tokenConsent`) live, given local entries are symlinks or pointer files and script entries are attacker-controlled clones? → A separate records directory `extensions/.records/<name>.yml` for every kind (changes spec FR4 install record location) (user, 2026-10-12)
- o11: On Windows, should a local install try `os.Symlink` first and fall back to a pointer file, or always write the pointer file like gh? → Always use the pointer file on Windows (gh parity, build-tagged) (changes spec FR5 local) (user, 2026-10-12)
- o12: Should a script install force LF checkout (`-c core.autocrlf=false -c core.eol=lf`) or leave line endings to the user's git config and the author's `.gitattributes`? → Force LF at clone (`-c core.autocrlf=false -c core.eol=lf`); the author's `.gitattributes` still wins (user, 2026-10-12)
- o13: On Windows, should `ado-<name>` with git mode 100644 still be accepted, since it runs through `sh` anyway? → Require mode 100755 on Unix only; on Windows accept a file with a shebang or a `.ps1`/`.cmd` sibling (user, 2026-10-12)
- o14: What should happen when git is older than 2.31 and the source is a private Azure DevOps HTTPS repo? → Fail with 'git >= 2.31 required for private Azure DevOps extensions' (user, 2026-10-12)
- o15: Should GitHub asset selection require the exact name `ado-<name>-<os>-<arch>[.exe]` or match by suffix `<os>-<arch>[.exe]` like gh? → Exact asset name first, then fall back to suffix match `<os>-<arch>[.exe]` (changes spec FR5) (user, 2026-10-12)
- o16: Which checksum sources should be accepted? → Accept `checksums.txt` and also a single asset ending in `_checksums.txt` (GoReleaser default name) (changes spec FR5) (user, 2026-10-12)
- o17: On darwin-arm64 with only a darwin-amd64 extension asset, should ado fall back to amd64 (Rosetta) like gh? → Yes: on darwin-arm64 fall back to a darwin-amd64 asset with a message, as gh does (user, 2026-10-12)

- o20: On darwin/arm64 or windows/arm64 with no native ArtifactTool build, what should happen? → Fall back to the amd64 ArtifactTool build with a one-line warning (user, 2026-10-12)
