## Phase 1: Pipeline Foundation — Timeline tree model and renderer

### q2. Azure DevOps Build timeline REST API 7.1: record types (Stage, Phase, Job, Task, Checkpoint, Checkpoint.Approval, Checkpoint.TaskCheck), parentId nesting, order, attempt and previousAttempts, how a retried stage/job appears, identifier field, issues (type error/warning, message), log.id and log url, state/result values, startTime/finishTime. How does a classic (designer) build timeline differ (no Stage level, Phase/Job only)? How do pending approvals/checks appear in the timeline?
**Answer:** The official 7.1 docs pin down the record fields and the enums. The record type strings, how Checkpoints nest, and retry behaviour are not documented by Microsoft; they come from consistent third-party code plus one Microsoft-owned script.

**Endpoint and SDK**
- Raw REST: `GET {org}/{project}/_apis/build/builds/{buildId}/timeline?api-version=7.1`; the optional `/{timelineId}` segment and `changeId`/`planId` parameters fetch a specific timeline, such as a previous attempt's.
- The pinned SDK wraps it as `build.Client.GetBuildTimeline(GetBuildTimelineArgs{Project, BuildId, TimelineId?, ChangeId?, PlanId?})`, sending api-version `7.1-preview.2` ("[Preview API]").
- The response is one flat `records[]` array; the tree is rebuilt client-side from `parentId`.

**Fields on build.TimelineRecord (SDK v7.1.0)**
- `id`, `parentId`, `type`, `name`, `order`.
- `state`: `pending | inProgress | completed`. `result`: `succeeded | succeededWithIssues | failed | canceled | skipped | abandoned`, null until completed.
- `startTime`, `finishTime`: `*azuredevops.Time`, null while not started or running.
- `attempt`, `previousAttempts[]` (each `{attempt, recordId, timelineId}`).
- `identifier`: "String identifier that is consistent across attempts".
- `issues[]` (`{type: error|warning, category, message, data}`), plus `errorCount`, `warningCount`.
- `log`: `{id, type, url}`; use `log.id` with `GetBuildLog`.
- Also `task`, `workerName`, `queueId`, `percentComplete`, `currentOperation`, `resultCode`, `details`.
- The build model has no `refName` (only the distributedtask model has it); don't plan on it.

**Nesting**
- The docs give the example "Stage is a parent of a Phase, Phase is a parent of a Job, Job is a parent of a Task", so a YAML run is Stage → Phase → Job → Task.
- Phase is mostly a design-time concept (one Job per Phase except matrix/multi-config). The renderer hides the Phase level and hangs Jobs under their Stage.
- A YAML pipeline with no `stages:` block still has a Stage; forgetop says it is named `__default`. Microsoft only documents `__default` for `Agent.JobName`, not for the stage. Verify with a live fixture.
- A classic designer build has no Stage records: root records are Phases ("Agent job 1") with `parentId` null, then Job, then Task (inferred from the spec and forgetop). The tree code treats a record whose parent is missing or null as a root and skips Phase levels when walking up.
- `order` is only "relative to other records": sort siblings by `order` within each parent.
- Logs (inference, not sourced): Task records carry `log.id`; Job records usually carry the full job log; Stage, Phase and Checkpoint records normally have `log: null`.

**Retries**
- `attempt` starts at 1 and goes up on each retry (matches `System.StageAttempt`/`System.JobAttempt`). `System.JobId` is "unique identifier for a single attempt of a single job", so record `id` changes per attempt and `identifier` stays the same.
- Inference: the base timeline holds one record per node with the latest attempt, and `previousAttempts[]` points to older records in other timelines (fetchable with `GetBuildTimeline(TimelineId=...)`). Whether old attempts can also appear side by side is undocumented: dedupe by (`parentId`, `identifier`, or `name` as fallback) and keep the highest `attempt`.

**Pending approvals and checks (not documented by Microsoft; nesting and type strings consistent across several codebases)**
- Structure: Stage → `Checkpoint` → children of type `Checkpoint.Approval` (manual approvals) or `Checkpoint.TaskCheck` (Invoke Azure Function/REST API, business hours, …).
- State values while waiting (low confidence, no source): the Stage is probably still `pending` with `startTime` null, and the Checkpoint and its children `inProgress`. Confirm with a live fixture.
- "Pending approval" = a `Checkpoint.Approval` record whose `state` is not `completed`. dev.to and forgetop use its `.id` as the `approvalId`; Microsoft's azure-sdk-tools script uses `.identifier`. Whether they are always equal is unverified: key on `identifier` with `id` as fallback, and let the fixture confirm.
- Other check kinds may appear as other `Checkpoint.*` types (names unconfirmed): render any unknown `Checkpoint.*` generically as "waiting: <name>".
- Classic builds have no Checkpoints; Classic Release approvals live in the Release API (FR12).

**Reuse:** `pkg/cmd/pr/shared/checks.go:237` already has `timeOf(*azuredevops.Time)`; promote it.

Confidence: fields and enums high (official); type strings, Checkpoint nesting and retry layout medium; Checkpoint states low.

## Phase 1: Pipeline Foundation — Pipeline and run references / Default pipeline resolution

### q3. Azure DevOps Pipelines API vs Build definitions API 7.1: IDs, folder path format, queueStatus (enabled/paused/disabled), process.type (1 classic designer, 2 YAML) and yamlFilename, the repository object on a definition (id, type TfsGit/GitHub, defaultBranch), filtering definitions by repositoryId/repositoryType and by name/path, includeLatestBuilds, and how to get a pipeline's default branch. **Answer:** Use the Build Definitions API (`_apis/build/definitions`, SDK `build`) for every definition concern: listing, name/path/URL resolution, the default pipeline, queueStatus, classic vs YAML, repository and default branch. **IDs**
- A pipeline ID is the build definition ID, and a run ID is the build ID. The official az CLI resolves a definition ID through the Build client and uses it either with `run_pipeline(pipeline_id=id)` (when `--parameters` is given) or with Build `queue_build(DefinitionReference(id=id))` otherwise. Run links everywhere use `_build/results?buildId=<runId>`. One ID space works for both APIs (medium: shown by Microsoft's tool, not stated in the REST docs).

**Definition fields (7.1)**
- `path` is the folder: root `\`, nested `\A\B`. The az CLI's `fix_path_for_api` strips a leading `/` and adds a leading `\` ("Path with no preceeding '\' is not correctly interpreted"); it does not convert inner `/`. Converting inner `/` to `\` is our own choice (the spec accepts both separators): normalize, add a leading `\`, treat the last segment as the name.
- `queueStatus`: `enabled | paused | disabled`. `paused` still lets users queue builds but the system won't start them; `disabled` refuses user queueing and CI/scheduled builds. `-a` should reveal both non-enabled states.
- `process.type` is documented only as "integer". The az CLI creates YAML definitions with `{"type": 2, "yamlFilename": ...}`. "Classic = 1" is unsourced, and other types exist (e.g. just-in-time). Detect YAML as `type==2 || yamlFilename != ""`, everything else classic.
- `repository`: `id` (Git repo GUID for Azure Repos), `type` (`TfsGit`, `GitHub`, also GitHubEnterprise, Bitbucket, Git), `defaultBranch` (full ref `refs/heads/main`), `name`, `url`.

**Filters**

### q4. **Build logs**
- **List:** `GET builds/{id}/logs` (`GetBuildLogs`) → `BuildLog{id,type,url,createdOn,lastChangedOn,lineCount}`.
- **One log:** `GET builds/{id}/logs/{logId}` with optional `startLine`/`endLine` (int64 in REST; `*uint64` in the SDK). Line numbering base is undocumented. - **Size limits:** none documented. Stream, don't buffer; don't use `lineCount` as a guard.

**Mapping timeline `log.id` to logs.** A timeline record's `log.id` is the `logId`. Go from the record to its log; never pair by position in the log list, which also holds logs that belong to no task. Caveat (medium): for steps with more than 8 MB of output, the agent creates one server log per uploaded page and re-points the record's `log` at each new one, so `log.id` may reference only the last page. Server-side merging is unverified; cover it as a risk (fallback to `GetBuildLogs` or the job log for such tasks).

**Job logs repeat their tasks' output.** In the agent, each task line is also written to the parent job's log when `LogsStreamingOptions.StreamToServer` is set, which is the default. Print task-record logs only for `--log`, `--log-failed` and `logs`, or output doubles.

**In-progress tasks usually have no log yet.** The agent writes step output to a local file in 8 MB pages (`PageSize = 8*1024*1024`), uploading a page when it fills or the step ends; each upload creates the server log, sends the content, then sets `Log` on the timeline record. Live console output goes through a separate web-console feed (SignalR, out of scope). So:
- A running task normally has `log == null`; FR6 `--follow` can only print each task's log once it completes.
- **Race (confirmed in agent source):** `Complete()` queues `state=completed` before `_logger.End()` uploads the log, so a record can briefly be completed with `log == null`. `--follow` keeps re-polling such records; stop waiting once the parent job record has a `log.id` (the job logger ends after its steps) or the run is completed.
- Skipped tasks never get a log.

## Phase 3: run, watch, cancel, rerun — watch/cancel/rerun

### q6. Azure DevOps 7.1: stage retry (PATCH build/builds/{buildId}/stages/{stageRefName} with state retry, forceRetryAllJobs, retryDependencies), which stages are retryable, errors; cancel a build (PATCH builds/{id} status cancelling) and its errors when already completed; reading the original run's templateParameters and queue-time variables (build.templateParameters, build.parameters JSON) for a full rerun; polling guidance and rate limits (TSTUs, Retry-After) for watch loops at 3s intervals.
**Answer:**
**Stage retry (`rerun --failed`)**
- `PATCH {org}/{project}/_apis/build/builds/{buildId}/stages/{stageRefName}` with 7.1 body `{"state":"retry","forceRetryAllJobs":false}` (`StageUpdateType` `cancel|retry`); 200 with no typed body; scope vso.build_execute. SDK `build.Client.UpdateStage` sends `7.1-preview.1`, makes `project` optional and discards the body; `UpdateStageParameters` has only `forceRetryAllJobs` and `state`.
- `retryDependencies` is not in the 7.1 contract or Go SDK v7.1.0; it appears in 7.2-preview.1 (which also adds state `run`) and the newer node SDK, backing Sprint 235's choice between "rerun this stage" and "rerun stage and dependents". Don't send it.
- Within the retried stage, with `forceRetryAllJobs=false`, failed jobs plus the jobs that depend transitively on them are re-attempted (Sprint 158). What happens to **downstream stages** when the 7.1 body has no `retryDependencies` is undocumented: Sprint 235 ("As before, you can still rerun a stage and its dependent stages") suggests the old default included dependents, but today's server may treat a missing field as `false`. Unverified; test it against a real org.
- `stageRefName` is the timeline record's `identifier`, not its GUID `id` or display `name` (DataDog's retry script selects `type=='Stage'` records and passes `$_.identifier`).
- Retryable stages: Microsoft documents that a failed stage can be retried and that "you cannot retry a stage that you explicitly cancel" (a 2019 gap, possibly fixed); DataDog also retries `canceled` stages (o10). Classic builds have no Stage records, so `--failed` there errors before any call (or see o1). Errors come back as ADO WrappedErrors, which `mapErr` → `HTTPError{StatusCode,Message,TypeKey}` already turns into readable messages; show them as-is.
- Ordering risk (depends on the unverified downstream default): if failed upstream stage A brings back its skipped dependents, a second PATCH for a failed dependent B may fail or collide; if the default no longer includes dependents, retrying A may leave skipped dependents unrun. Pick failed stages whose ancestors are not also being retried, or retry in timeline `order` and report each result (as DataDog does with retried/failed/skipped).
- `PATCH builds/{id}?retry=true` (`UpdateBuildArgs.Retry`) exists but its behaviour is undocumented; don't rely on it.

**Cancel**
- `PATCH {org}/{project}/_apis/build/builds/{id}` with `{"status":"cancelling"}`; returns the updated Build. SDK `UpdateBuild(Build{Status:&cancelling})` (`omitempty` keeps the body minimal). The az CLI does the same with no client-side check.
- No source documents the error for cancelling a completed build. GET first; if `status==completed`, print an error and exit 1 without PATCH; treat a returned `status==completed` the same. Already `cancelling` needs a decision (o11).

**Full rerun inputs**
- The Build GET returns `templateParameters` (SDK `*map[string]string`), `parameters` (string holding a JSON object of queue-time variables), `sourceBranch`, `sourceVersion`, `definition.id`: one GET suffices.
- YAML rerun: Pipelines `RunPipeline` with `templateParameters` copied straight across, `variables` = `map[string]Variable{value,isSecret}` from the decoded `parameters`, `resources.repositories.self = {refName: sourceBranch, version: sourceVersion}`. Classic rerun: Build queue with the same `parameters` string.
- Prefer the Build GET over Pipelines `GET runs/{id}`: `Run.templateParameters` is `map[string]interface{}` (mismatch with the request type), and a Q&A user reports the Runs **List** endpoint returns `variables` empty (weaker evidence, different endpoint).
- Unconfirmed: whether `parameters` keeps secret queue-time values, and whether `templateParameters` lists only overrides or also defaults.

**Polling and rate limits**
- Global limit 200 TSTUs per sliding 5-minute window; "One TSTU represents the average load generated by a typical Azure DevOps user over five minutes"; delays "up to 30 seconds"; blocked requests get 429 with TF400733.
- Headers: `Retry-After`, `X-RateLimit-Resource`, `X-RateLimit-Delay`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `X-RateLimit-Cost`. Microsoft notes `Retry-After` can arrive on HTTP 200 ("The response still returns HTTP 200, so retry logic isn't required"). No fixed per-request cost or poll interval is published, but `X-RateLimit-Cost` reports the TSTUs a request consumed, so cost can be measured.
- The shared transport already honours `Retry-After` on any status (capped at 1 min), backs off 1s on `X-RateLimit-Remaining: 0`, retries 429 up to 3 times and delays later requests through `notBefore`. The watch loop needs no throttle code.
- 3s interval with one build GET plus one timeline GET per tick is 40 requests/min of cheap reads. Keep `time.Ticker` (drops ticks while the transport waits). To cut cost, poll only the timeline per tick and GET the build at the end. `changeId` on Timeline Get is undocumented; leave it out.

### q7. Azure DevOps build artifacts API 7.1: GET builds/{id}/artifacts resource.type values (Container, PipelineArtifact, FilePath/file share, others), resource.downloadUrl and $format=zip, redirects to blob storage (signed URLs) and whether the Authorization header must be dropped on cross-host redirect, large artifact limits, zip layout (top-level artifact folder), and safe extraction (zip-slip) guidance in Go archive/zip.
**Answer:**
**1. Listing and resource.type.** `GET {org}/{project}/_apis/build/builds/{id}/artifacts?api-version=7.1` (`&artifactName=X` for one). The docs describe `resource.type` only as "File container, version control folder, UNC path, etc."; values in use come from the agent source:
- `Container`: legacy PublishBuildArtifacts; `data` is `#/{containerId}/{rootPath}` (e.g. `#/922702/drop`).
- `PipelineArtifact`: PublishPipelineArtifact in dedup; `data` is a dedup id; `properties` holds RootId, artifactsize, HashType.
- `FilePath`: file share; agent constant is lowercase `filepath`; `downloadUrl` is a `file://` UNC URI, `data` the UNC path.
- Rare: `VersionControl`, `GitRef`, `TfvcLabel`, `SymbolStore`.
The agent compares types case-insensitively (use `strings.EqualFold`) and treats `type == null && id == 0` as a file share (server bug 378900). Other types get "skipped: unsupported artifact type X". `artifactsize` allows showing or checking size before download.

**2. What to download.** Use `resource.downloadUrl` as given, not SDK `GetArtifactContentZip` (`build/client.go:920`, `7.1-preview.5`, only the dev.azure.com route; a .NET blog reports it throwing). Container: same build endpoint plus `&%24format=zip` on dev.azure.com. PipelineArtifact: `https://artprod<region>.artifacts.visualstudio.com/.../_apis/artifact/<id>/content?format=zip`. If a Container `downloadUrl` is empty, fall back to `builds/{id}/artifacts?artifactName=X&%24format=zip`. Plain GET with the authenticated `*http.Client`, streamed to a temp file (`zip.NewReader` needs `io.ReaderAt` plus size; artifacts can be GBs).

**3. Redirects and Authorization.** Microsoft doesn't document whether these endpoints redirect; the Q&A workaround uses `curl -L`, and the allow-list doc names `*.blob.core.windows.net`, `*.visualstudio.com`, `*.dedup.microsoft.com`. Handle both a direct stream and a redirect to a SAS-signed blob URL. Go's `http.Client` drops Authorization on cross-domain redirects only for headers set on the original request; ado's transport sets Authorization itself on every hop (`api/http_client.go:108-124`), so what protects us is the token callback (`pkg/cmd/auth/shared/http_client.go:45-50`), which returns no token unless `IsADOHost` (`:15-24`): dev.azure.com and `*.visualstudio.com` (incl. artprod) yes, `*.blob.core.windows.net` no. Nothing new is needed; add a test that an httpmock 302 from artprod to `x.blob.core.windows.net` arrives without Authorization. `*.vsblob.visualstudio.com` also gets the token (Microsoft-owned ADO domain; acceptable). Cosmetic caveat: a 401/203 from any host becomes an `AuthError` naming the host (`api/http_client.go:170-175`); expired SAS URLs usually return 403.

**4. Signed URLs leak today in two places** (conflicts with the NFR "Signed download URLs are never printed"):
- (a) `--debug` prints `req.URL.Redacted()` (`api/http_client.go:217`), which hides only the userinfo password, not the query, so a redirected blob request's SAS `sig=` is printed. Fix once in `logRequest` (drop `RawQuery`; scope per o15).
- (b) `client.Do` errors are `*url.Error` whose `Error()` includes the full URL; transport errors such as `AuthError` arrive wrapped the same way. Wrap download errors as `fmt.Errorf("downloading %s: %w", name, urlErr.Err)`. Never echo `downloadUrl`.

**5. Limits.** No documented size limit. Container `$format=zip` is built on the fly, so first byte can be slow: no `http.Client.Timeout`, cancel through the command context. A 2025 incident (HTTP 500 on artifact download) shows transient failures; report with the artifact name, no retry logic. Optional zip-bomb guard: compare written bytes with `f.UncompressedSize64` using `io.CopyN`.

**6. Zip layout.** Undocumented. In practice both Container and PipelineArtifact zips contain one top-level `<artifactName>/` folder (unverified). If every entry's first path element equals the artifact name (case-insensitive), strip it; otherwise extract as-is. Confirm live in Phase 4 verification.

**7. Safe extraction (Go 1.25.8+, stdlib only)**
- (a) Validate the artifact name before it becomes a directory (gh uses `safepaths.ValidateChild(a.Name)`).
- (b) Per `zip.File`: strip a trailing `/` for directories, reject names containing `\`, require `fs.ValidPath(name)`, then `filepath.Localize(name)` (Go 1.23+; result is always `filepath.IsLocal`, which also rejects Windows reserved names like NUL).
- (c) Write through `os.OpenRoot(dest)` with `root.MkdirAll` and `root.OpenFile(rel, O_CREATE|O_EXCL|O_WRONLY, 0o644)`, guarding against symlink escapes too.
- (d) Skip symlink (`f.Mode()&fs.ModeSymlink`) and other non-regular entries.
- Don't rely on `ErrInsecurePath`: it fires only with `GODEBUG=zipinsecurepath=0`. GO-2026-4970 (Unix symlink plus trailing slash; fixed in 1.25.12/1.26.5) and GO-2026-6604 (Windows junction with `Root.MkdirAll`; fixed only in 1.26.9/1.27.2, no 1.25.x fix) matter only if the target already holds attacker-made links. CI uses `go-version: stable`; extracting into a fresh directory avoids both. `--clobber` should remove and recreate `<dir>/<artifact>` (o14).

**8. Reuse.** `api.NewSDKClient` plus `build.ClientImpl.GetArtifacts` for the list (`BuildArtifact`/`ArtifactResource` in `build/models.go:86-98,241-250`). Nothing in the repo does zip or path confinement yet; FR6 `logs -o` needs the same confinement, so write one helper (os.Root plus Localize) in `pkg/cmd/pipeline/shared`.

**6. Security risks, mapped to code**
- **Token to the wrong host — already handled:** `shared.HTTPClient` sends the credential only to ADO hosts. Keep downloads on it; add a test that a redirect to `*.blob.core.windows.net` has no Authorization header.
- **Signed URL leak via `--debug` — needs a fix:** `req.URL.Redacted()` masks only the userinfo password, so a redirected SAS query is printed. Fix in `logRequest` (e.g. drop RawQuery when the request carries no Authorization; o15). Unwrap `*url.Error` in download errors. Never request `$expand=signedContent` (Pipelines Artifacts returns "limited-time anonymous access" URLs) and never expose `downloadUrl` in JSON.
- **Zip-slip:** `archive/zip` rejects non-local names only with `GODEBUG=zipinsecurepath=0`. Extract and write `-o` files through `os.Root` (Go 1.24+; go.mod 1.25.8), whose methods error on names or symlinks escaping the root (Windows reserved-name handling and `Root.MkdirAll` were not confirmed from the fetched docs; see q7 for `filepath.Localize`). Skip non-regular entries, spool the zip to a temp file, cap bytes per entry.
- **`--output` names:** sanitize separators, `:*?"<>|`, control characters, trailing dots/spaces and Windows reserved names before `os.Root`, so they don't just error on Windows.
- **Log size and memory:** stream `GetBuildLog` (`io.ReadCloser`); avoid `GetBuildLogLines` (`*[]string`). For the `job<TAB>task<TAB>` prefix don't use a default `bufio.Scanner` (64 KiB token limit); use `bufio.Reader.ReadString`/`ReadSlice` or `Scanner.Buffer`. The 429 backoff (api/http_client.go:149-167) covers many per-log GETs.
- **Terminal escapes (low):** raw logs printed to a TTY can carry escape sequences.

## Open questions

- o2: Which failure mark should pipeline and release output use? — `pr checks` and `workitem assign` print "X", the spec lists ✗; the Phase 1 status-model tests pin it (options: ✗ as in the spec / X to match `pr checks` and the work item commands) — resolved
- o3: Should `view`/`watch` show attempt history for retried stages/jobs, or only the latest attempt? — older attempts need an extra timeline fetch each and more fixtures (options: latest attempt only, with "attempt N" next to the node / latest plus a `--attempt N` flag fetching `previousAttempts[].timelineId`) — resolved
- o4: For YAML runs with no stages (implicit `__default` stage), how should the tree look? — decides the JSON `stages` shape and alignment between classic and stage-less YAML (options: hide the implicit stage and show jobs at the top level, as with classic / show it as a stage named after the pipeline or "Jobs") — resolved
- o5: Should default-pipeline resolution skip disabled (and paused) definitions? — a repo with one live and one old disabled pipeline would otherwise hit the "several" path (options: include all regardless of queueStatus / exclude disabled only / exclude disabled and paused) — resolved
- o6: When `ado pipeline run` gets no `-b`, should ado send the default branch explicitly or let the server pick it? — explicit lets ado print it and keeps tests deterministic, at the cost of one GET (options: read `repository.defaultBranch` (fallback: Git repo default) and send it / omit it and let the server decide, like the az CLI) — resolved
- o7: Should `ado pipeline list -b <branch>` also find PR-validation runs for that branch (sourceBranch `refs/pull/N/merge`)? — decides whether developers see the runs they expect; one option adds Git API calls (options: match sourceBranch only and document `-e pullRequest` / also look up PRs for the branch and query `refs/pull/<id>/merge` / filter PR runs client-side via triggerInfo) — resolved
- o8: With `-c/--commit`, how far should client-side paging go? — the Build list API has no commit filter, so an unbounded scan can be slow (options: until `-L` matches or the token runs out / cap at N pages (e.g. 10 × 100) and warn results may be incomplete / combine with `-b`/definition to narrow and cap pages) — resolved

- o10: Which stages should `rerun --failed` retry? — the spec says failed only; Microsoft documents a gap for explicitly canceled stages, DataDog retries them anyway; changes the "no failed stages" error and fixtures (options: only `failed` / `failed` and `canceled` / `failed`, `canceled` and `partiallySucceeded`) — resolved
- o11: What should `ado pipeline cancel` do when the run is already `cancelling`? — FR7 covers only completed (options: print a message and exit 0 / error and exit 1, like completed / send the PATCH again and report success) — resolved
- o12: Should `rerun --failed` be allowed while the run is still in progress? — no source says whether a stage can be retried before the run completes (options: only once the run is completed, else error "run is still in progress" / allow it and let the server decide) — resolved
- o13: With a single `-n`, should `download` extract into `<dir>/<artifact>` (spec FR9) or directly into `<dir>` like `gh run download`? — scripts ported from gh expect files directly in `-D` (options: keep the spec and document it in gh-differences / match gh: single `-n` into `<dir>`, several into `<dir>/<artifact>`) — resolved
- o14: What should `--clobber` do when `<dir>/<artifact>` exists? — extracting over a tree can follow pre-existing links (GO-2026-4970/6604) and leaves stale files (options: remove and re-extract into a fresh directory / overwrite files in place, keeping extras) — resolved
