## Phase 1: Repo Foundation, `repo list`, `repo view` — phase

### q1. Codebase reuse for the repo track: pkg/cmdutil Browser/ResolveBrowserLauncher (incl. the WSL opener), how the existing --web flags in pkg/cmd/pr/{list,view,create,diff,comment,checks} open the browser and print 'Opening ... in your browser.' (to consolidate into the planned cmdutil.OpenInBrowser), internal/adocontext parsing for repo references (repo, project/repo, org/project/repo, URL), internal/config per-host keys (for a new git_protocol key) and pkg/cmd/config/shared options, pkg/cmd/auth/shared.HTTPClient, the prompter, internal/git client and api package conventions. What exists, what is missing, where new code should live.
**Answer:** Most of Phase 1 can reuse existing code. Three plan items are already done or are wrong.

**1. Browser (already built; the plan's "add browser config key" is already done)**
- `cmdutil.Browser` is an interface with one method, `Browse(url)`. `ResolveBrowserLauncher` picks the browser in this order: `ADO_BROWSER`, then config `browser`, then `BROWSER`.
- `NewBrowser` uses go-gh `pkg/browser` when a launcher is set. Otherwise it uses `systemBrowser`, which on WSL calls `wslview`, falling back to `rundll32.exe url.dll,FileProtocolHandler`, and elsewhere calls cli/browser `OpenURL`. `NewFactory` wires `f.Browser` to all of this lazily.
- The `browser` config key already exists in `pkg/cmd/config/shared` Options. So "add `browser` config key" and "implement with go-gh pkg/browser" in the plan's helper task are done. Only the print-and-open wrapper is missing.
- Mismatch: spec FR7 (spec.md:62) and plan.md:15 say `BROWSER` env, then config, then OS default. The code does `ADO_BROWSER`, then config, then `BROWSER`, which mirrors gh (`GH_BROWSER`, then config, then `BROWSER`). One of them has to change (o1).

**2. Existing `--web` flags (six copies of the same block)**
- `pr view`, `list`, `create`, `diff`, `comment` and `checks` each contain: `if ios.IsStdoutTTY() { fmt.Fprintf(ios.ErrOut, "Opening %s in your browser.\n", u) }; return f.Browser.Browse(u)`.
- New helper, about 5 lines, in `pkg/cmdutil/browser.go`: `func OpenInBrowser(f *Factory, url string) error`, keeping the stdout-TTY check, writing to stderr and printing the full URL.
- gh differences: gh writes `text.DisplayURL(url)` (no scheme). `gh pr view` writes to stderr (guarded by its `connectedToTerminal` check), while `gh browse` writes the message to stdout.
- Each pr test file defines its own small browser stub (e.g. `viewBrowser`). A shared stub is optional. Moving the six commands onto the helper is planned for Phase 4 but is cheap in Phase 1. Five test assertions check the "Opening" line.

**3. adocontext (partial; the main gap)**
- `Repo{Host,Org,Project,Name}`.
- `ParseRemoteURL` handles HTTPS on dev.azure.com and `{org}.visualstudio.com` (including DefaultCollection, team segments and `_full`/`_optimized`), SSH v3, legacy vs-ssh `_ssh` paths and ssh aliases. It drops userinfo and never echoes the input (a PAT could be in it).
- Web URLs copied from a browser do **not** parse as-is: `ParseRemoteURL` rejects any input containing `?` or `#`, accepts only https or ssh, and `parseHTTPS` needs exactly one segment after `_git`. So `.../_git/repo?path=/README.md`, `?version=GBmain`, `.../_git/repo/pullrequest/5` and `/commit/<sha>` are rejected. `ParseRepoRef` must strip query, fragment and trailing sub-paths first, as `pr/shared/finder.go` `parseURL` already does for `/pullrequest/N`.
- `ResolveBaseRepo` resolves -R, then `ADO_REPO`, then origin, upstream, first ADO remote. Spec.md:50 inserts `ado-resolved` between `ADO_REPO` and origin; that is Phase 3 (q7).
- `parseRepoArg` (unexported) parses `[ORG/]PROJECT/REPO`, fills gaps from `ADO_ORG`/`ADO_PROJECT`, hardcodes host dev.azure.com and does not accept URLs.
- Missing for FR2/FR3: accepting a URL; a bare `repo` taking org, project and host (e.g. visualstudio.com) from the current context first; a config default-org fallback. No `org`/`default_org` config key exists anywhere (o2).
- Suggestion: put `ParseRepoRef(arg string, base func() (Repo, error)) (Repo, error)` in `internal/adocontext`, not `pkg/cmd/repo/shared`. It needs the unexported `validSegment`/`parseRepoArg`, and `browse`/`clone`/`delete`/`set-default` will reuse it. Order: URL (cleaned) via `ParseRemoteURL`; otherwise split on `/` and fill from base, then env, then config.

**4. Config (`git_protocol` is Phase 2, but this is where it goes)**
- `internal/config` already supports per-host keys: `Get(host,key)` tries the host value, then the global value, then defaults; there are also `Set`/`Unset`/`Hosts`. Hosts are keyed by the original remote host.
- `ado config set` already validates through `shared.Find` + `Option.Validate` and supports `--host`.
- Adding `git_protocol` is one `Options` entry: `{Key: "git_protocol", Default: "https", AllowedValues: ["https","ssh"]}`, read with `Option.Value(cfg, repo.Host)`.
- `ssh.dev.azure.com` and `dev.azure.com` are different host keys.
- `TestFind` hardcodes the key list (options_test.go:26 checks the error contains "browser, editor, entra_client_id, prompt"), so it must be updated when a key is added.

**5. Auth and URLs (reuse as-is)**
- `authshared.HTTPClient(ctx, f, host, org)` looks up the credential and only sends the token to ADO hosts. `authshared.OrgURL(host, org)` gives the org base URL; `OrgFromContext` and the `NoOrg` message exist too.
- Pattern to copy: `prshared.NewClient` calls `HTTPClient`, then `api.NewPRClient(hc, OrgURL(...), project, repo)`.
- Repo web URL: `prshared.RepoURL(repo)`. Move or wrap it into a neutral package (adocontext or repo/shared) so `repo view -w` and `browse` don't import `pr/shared`.

**6. API conventions (`api/repo.go` is new)**
- `api/pr.go` sets the pattern: a client struct wrapping an SDK `git.Client` plus Project/Repo, built from `NewSDKClient(hc, orgURL)`; errors pass through `mapErr` into `*HTTPError`; `IsNotFound` exists.

- SDK v7.1.0 has `GetRepositories` (Project optional; nil lists the whole org with `repo.Project.Name` filled), `GetItems`, `GetItemContent`, `CreateRepository`, `DeleteRepository`, `GetRecycleBinRepositories`, `DeleteRepositoryFromRecycleBin` and `CreatePush`. `GitRepository` has `IsDisabled`, `IsFork`, `ParentRepository`, `Size`, `SshUrl` and `WebUrl`. No gitignore-templates method exists (q4).
- Proposal: `api/repo.go` with `RepoClient{Git git.Client; Project string}` and `NewRepoClient(hc, orgURL, project)`; methods `ListRepositories`, `Repository`, `RootItems`, content fetch.
- Tests: `pkg/httpmock` (`Registry`, `REST`, `JSONResponse`, `StubLocations`/`StubResourceAreas` for SDK routing).

**7. Prompter, git, output**

### q2. Azure DevOps Git Repositories REST API and azure-devops-go-api v7.1.0: listing repositories per project vs across the whole organization (GET {org}/_apis/git/repositories), fields isDisabled, isFork, size, remoteUrl, sshUrl, webUrl, parentRepository, defaultBranch (null for empty repos), includeHidden/includeLinks, paging; SDK functions (GetRepositories, GetRepository); how disabled repositories behave for items/commits calls.
**Answer:** Two SDK calls cover Phase 1: `GetRepositories` with or without a project for `repo list`, and `GetRepositoryWithParent` (not plain `GetRepository`) for `repo view`. The API has no paging, so `--limit` and all filters run in our code.

1. **Per project vs whole organization.** One endpoint with an optional `{project}` segment: `GET {org}/{project}/_apis/git/repositories` or `GET {org}/_apis/git/repositories` (Microsoft's own sample uses the org form; each item carries `project{id,name}` for the project column). `git.GetRepositoriesArgs{Project *string, IncludeLinks, IncludeAllUrls, IncludeHidden *bool}` covers both: a nil `Project` drops the optional route segment. The SDK sends `api-version=7.1-preview.1` and unwraps `{count,value}`.
2. **No paging.** The 7.1 List call has no `$top`, `$skip` or continuation token; only `includeLinks`, `includeAllUrls`, `includeHidden` (all default false). `-L/--limit` (default 30), name sort, `--match`, `--fork`/`--source` and `--disabled` run client-side on one response: filter, then sort, then limit. Which repos count as "hidden" is undocumented; leave `includeHidden` unset (matches the web list). Leave `includeLinks` unset too.
3. **Fields.** `git.GitRepository` has every FR1 field as a nil-able pointer: `IsDisabled`, `IsFork` (Microsoft's `az repos show` sample returns `"isFork": null` for an ordinary repo, so nil = not a fork), `Size *uint64` (compressed bytes), `RemoteUrl`, `SshUrl`, `WebUrl`, `ParentRepository *GitRepositoryRef`, `DefaultBranch` (full ref, e.g. `refs/heads/main`), plus `IsInMaintenance`. The REST List sample itself shows only id, name, url, project, defaultBranch and remoteUrl; `webUrl`, `sshUrl`, `size`, `isDisabled` come from the schema and the `az repos show` output, so tests must handle each being absent. In the List sample `AnotherRepository` has no `defaultBranch`; treating nil `defaultBranch` as "empty repository" is an inference (consistent with common behaviour, not documented). `repo view` should then skip the README lookup; `repo list` shows it blank. Map into our own JSON struct (nil → false/0/""), never serialize the SDK struct; strip `refs/heads/` for display.
4. **`remoteUrl` can contain a username.** The `az repos show` sample on the repository-settings page returns `https://fabrikamprime@dev.azure.com/...`; the REST List sample has no user part. So it happens only sometimes. Never a token.
5. **Fork parent only on request.** `GetRepositoryWithParent` (`?includeParent=true`, required, "Only available in authenticated calls") exists, so List and plain Get very likely leave `parentRepository` out (unverified; the `az repos show` sample's `"parentRepository": null` is for a non-fork). `repo view` and clone should use `GetRepositoryWithParent(IncludeParent=true)`; same location id, so the existing location stub applies. For `repo list --json parentRepository` see o4.
6. **`GetRepository`.** `GetRepositoryArgs{RepositoryId (name or ID, required), Project (optional)}`. Without project the route is `{org}/_apis/git/repositories/{id}` (already used for lookups by GUID). Lookups by name should always pass the project.
7. **Disabled repos.** Microsoft: disabling "Disable[s] access to the repository, including builds and pull requests, but keep[s] the repository discoverable with a warning", so they appear in List/Get with `isDisabled: true`. The status code items/commits calls return for a disabled repo is undocumented. Check `IsDisabled` before any items call; errors still go through `mapErr`.

Reuse: `api/pr.go:305-315` wraps `GetRepository` with and without project; `mapErr` at `api/pr.go:45`; tests stub location `225f7195-f9c7-4d14-ab28-a83f7ff77e1f` (route `{project}/_apis/git/repositories/{repositoryId}`) at `api/http_client_test.go:171-180`, usable for List, Get and GetWithParent. New code in `api/repo.go` following `PRClient`.

## Phase 1: Repo Foundation, `repo list`, `repo view` — `ado repo view`

### q3. README retrieval and rendering: Azure DevOps Items API to list the repository root (recursionLevel OneLevel) and fetch a file's content on a branch (versionDescriptor, includeContent / $format=text), case-insensitive README* discovery, empty repositories; and charmbracelet/glamour: current version, whether it is pure Go (CGO_ENABLED=0), dependency and binary size impact, auto dark/light style detection, Windows terminal behaviour, word wrap width.
**Answer:**
**Items API**
1. **List the root.** `git.Client.GetItems(ctx, git.GetItemsArgs{RepositoryId, Project, ScopePath: "/", RecursionLevel: &git.VersionControlRecursionTypeValues.OneLevel, VersionDescriptor: ...})` → `GET .../items?scopePath=/&recursionLevel=oneLevel&versionDescriptor.versionType=branch&versionDescriptor.version=<name>`. The response includes the root folder itself (`path:"/"`, `isFolder:true`) plus its direct children: drop `isFolder` entries, name = `strings.TrimPrefix(path, "/")`. Each blob carries an `objectId`. Without `VersionDescriptor` the server uses the default branch, so send it only with `-b`. Ref names must be bare: strip `refs/heads/` from `DefaultBranch` as `api/pr.go:355` already does.
2. **Fetch content.** (a) `BlobContent(ctx, objectId)` (api/pr.go:283) with the listing's `objectId` — raw bytes, one round trip, no new wrapper (recommended; test like api/blobs_test.go:26-61). (b) Generalise `ItemContentAt` (api/pr.go:293) to a branch descriptor. Neither `includeContent` (content inside JSON) nor `$format=text` is needed; `$format` only accepts `json`/`zip`.
3. **Find the README.** Match `strings.HasPrefix(strings.ToLower(name), "readme")`; several can match. Prefer a markdown extension (`.md`, `.markdown`, `.mdown`, `.mkdown`, gh's `isMarkdownFile` list), else first in sorted order (o8). gh matches suffixes case-sensitively; lowercasing the extension first is a deliberate deviation, not parity. Render with glamour only when the file is markdown **and** stdout is a TTY; piped output skips glamour entirely and prints raw (spec.md:25). Non-markdown READMEs print raw. Strip a UTF-8 BOM and convert CRLF → LF before rendering.
4. **Empty and disabled repos.** The Items API error for an empty repo is undocumented. Microsoft's Terraform provider treats a repo as "not initialized" when `DefaultBranch` is nil/empty and `Size` is nil/0. So: no `DefaultBranch` and no `-b` → skip Items and show the missing-README / empty-repo note. Treat a 404 from the listing (`api.IsNotFound`, api/pr.go:38), e.g. a bad `-b`, the same way; stub both 404 and 400 in tests. Disabled repo → no Items call.

**glamour**
- **Versions.** `charm.land/glamour/v2` v2.0.1 (2026-06-12; v2.0.0 2026-03-09); `github.com/charmbracelet/glamour` v1.0.0 (2025-11-24); v0.10.0 (2025-04-16), which gh trunk and go-gh v2.16.2's `pkg/markdown` pin, so it is already in the module graph via go-gh.
- **Pure Go.** Deps are goldmark, goldmark-emoji, chroma/v2 (+ dlclark/regexp2), bluemonday (+ gorilla/css, aymerick/douceur), charmbracelet/x, x/text — all pure Go; termenv, lipgloss v1/v2 and reflow are already indirect. Not compiled: add `CGO_ENABLED=0 go build ./...` as a check.
- **Binary size.** Current `bin/ado` is 25.2 MB. Chroma's lexers dominate; one unofficial measurement (with a newer chroma than v0.10 pins) suggests +5 to 7 MB. Low confidence until measured before/after.
- **Dark/light detection.** v0.10's `WithAutoStyle` checks `os.Stdout` directly, ignoring IOStreams/`ADO_FORCE_TTY`. Pick the style yourself: `notty` when the TTY has colour disabled, else `dark`/`light`, honouring `GLAMOUR_STYLE`. Both detection paths query the terminal: termenv's `HasDarkBackground()` on Unix sends OSC 11 + DSR and waits up to 5 s (skipped for TERM screen/tmux/dumb) and writes to `os.Stdout`; v2 removed `AutoStyle` (default `dark`) and `lipgloss.HasDarkBackground(in, out)` uses raw mode, OSC 11 + DA1, 2 s timeout, dark on error. v2 also leaves colour downsampling to the caller. Whichever version: detect only when stdout is a real TTY, and let `GLAMOUR_STYLE` skip detection.
- **Windows.** termenv's Windows background detection always reports black (never waits); lipgloss v2 really queries, opening `CONIN$`/`CONOUT$` when redirected. Neither glamour version enables virtual terminal processing, so legacy conhost shows raw escapes unless the program calls `termenv.EnableWindowsANSIConsole`, `lipgloss.EnableLegacyWindowsANSI` or `SetConsoleMode`. ado's existing ColorScheme output already has this gap; nothing in the repo enables VT today.
- **Word wrap.** glamour defaults to 80 columns. gh uses terminal width capped at 120 (`GH_MDWIDTH` overrides). Use `glamour.WithWordWrap(min(ios.TerminalWidth(), 120))` (`TerminalWidth()` falls back to 80), plus `WithEmoji()`, `WithPreservedNewLines()`, `WithTableWrap(false)` — what go-gh's `markdown.Render` does.
- **Testing.** v0.10's default colour profile is TrueColor, so test output is deterministic.

### q6. Cloning Azure DevOps repositories from a CLI: building HTTPS vs SSH clone URLs from the repository object (remoteUrl includes an org@ userinfo; sshUrl format), HTTPS authentication with Git Credential Manager without putting tokens in URLs, adding the parent as an upstream remote for forks (parentRepository.remoteUrl), passing extra git flags after `--` safely (argument injection with names starting with '-'), target directory naming with spaces, and how gh repo clone behaves (protocol config, upstream remote, -- flags).
**Answer:**
1. **Clone URL.** Fetch the repo with `GetRepositoryWithParent(includeParent=true)` (7.1-preview.1 in the SDK; needed anyway for `isFork`/`parentRepository`) and clone from its URL fields, never built from parts.
   - `git_protocol=https` → `remoteUrl`; `ssh` → `sshUrl` (`git@ssh.dev.azure.com:v3/{org}/{project}/{repo}`; legacy `vs-ssh.visualstudio.com` still works).
   - `remoteUrl` often is `https://{org}@dev.azure.com/...` (the Learn clone page uses that form; REST samples omit it). Keep `org@` as given: it is a username hint, not a secret. GCM reads the org from the path first and falls back to the username when `credential.useHttpPath` is off; removing it would break those users.
   - Existing code already does this: `SourceRepo` uses the API `RemoteUrl` verbatim with a `RepositoryByID` fallback; `pr checkout` fetches from it.
   - `ParseRemoteURL` drops userinfo and %-decodes segments; use it to validate any URL and get org/project/name. Never echo the URL (`errNotADO` convention).
   - User-given full URLs: parse for the fork lookup, then clone the user's string as given. gh instead rebuilds the URL from the API repo with the scheme the user typed — record in `gh-differences.md`.
   - Per-host `git_protocol` (q1). Risk: an SSH-derived context has host `ssh.dev.azure.com`, so a value set with `--host dev.azure.com` won't match.
2. **Authentication.** ado sets no `credential.helper`, `GIT_ASKPASS` or `GIT_TERMINAL_PROMPT` and puts no token in any URL; git uses the user's GCM or SSH keys. This differs from gh, whose `Client.Clone` runs through `AuthenticatedCommand` and injects gh's own credential helper — record in `gh-differences.md`.
   - Gap: `internal/git` `run()` buffers stdout and stderr, so clone progress won't show. `repo clone` needs a git call streaming to IOStreams with stdin attached. `Client.Run`'s signature `func(ctx, dir, args) ([]byte, error)` can't carry IOStreams, so the streaming variant needs its own stub hook or tests lose clone/fetch argv coverage.
   - Gap: `git.Error.Error()` prints `git <args>` when stderr is empty (as when streamed), which would print the clone URL. After a streamed git failure return `cmdutil.SilentError`. git's own stderr may still print the URL (`fatal: unable to access '...'`): harmless for URLs ado builds, not for user-typed URLs with a password (o14).
   - `HandleError` exits 1 for these errors, so "git failure exit code propagated" means non-zero (1), as gh.
3. **Forks.** gh: `git remote add -t <parentDefaultBranch> <name> <url>`, `git fetch <name>`, `git remote set-branches <name> '*'`, `git config --add remote.<name>.gh-resolved base`; `-u/--upstream-remote-name` (default `upstream`, `@owner`) and `--no-upstream` (exclusive; marks origin as base). For ADO: use `parentRepository.remoteUrl`/`.sshUrl`, falling back to `RepositoryByID`; `GitRepositoryRef` has no `defaultBranch`, so skip `-t` and do plain `remote add` + `fetch`. Run them via `git.Client{Dir: cloneDir, Run: f.GitClient.Run}`. `gittest.Runner.Run` ignores its dir argument and records only joined args, so asserting "runs in the clone dir" needs the Runner to record dir (small sub-task). ado-resolved / `--no-upstream` → o12.
4. **Extra flags after `--`.** Split with cobra `cmd.ArgsLenAtDash()` (gh instead guesses the first non-`-` extra arg is the directory). Run `git clone <gitflags...> -- <url> [<dir>]`. ADO naming forbids a leading `_`, leading/trailing `.` and some characters, but allows a leading `-` and spaces; on git 2.43 `git clone -- https://…/-evil` clones into `-evil`. gh puts no `--` before URL/dir. Also use `git remote add -- <name> <url>`. User flags after `--` pass through unchanged.
5. **Target directory.** git doesn't decode `%20` (git 2.43: URL ending `My%20Repo` → dir `My%20Repo`). Compute it: user `<directory>`, else the decoded repo name from `ParseRemoteURL` (`.git` suffix with `--bare`, as gh); pass it explicitly (o13). `exec` uses no shell, so spaces need no quoting. Reject `.`/`..` and names where `filepath.Base(name) != name` — relevant only for user-typed URLs or directories, since ADO names can't start/end with `.` or contain `/ \ :`.
6. **Docs:** Azure Repos does not support Git LFS over SSH.

## Phase 3: `repo delete` and `repo set-default` — `ado repo set-default` and Context resolution update

### q7. How gh implements `gh repo set-default` (git config remote.<name>.gh-resolved = base, --view, --unset, interactive selection) and how to fit an equivalent `remote.<name>.ado-resolved` into this codebase's base repo resolution (internal/adocontext ResolveBaseRepo order -R > ADO_REPO > origin > upstream > first ADO remote) and the newer cmdutil.Factory.BaseRepoFromGit(); git config read/write via internal/git.
**Answer:**
**How gh does it (trunk)**
- **Storage.** `remote.<name>.gh-resolved`. Read: `git remote -v`, then `git config --get-regexp ^remote\..*\.gh-resolved$` (exit 1 = none), copied into `Remote.Resolved`. Write: `git config --add remote.<name>.gh-resolved <value>`. Clear: `git config --unset ...`.
- **Resolution.** `Resolved == "base"` returns that remote; a non-empty `owner/repo` builds a repo on the remote's host. Nothing set: when gh can't prompt it takes the first sorted remote (upstream 3, github 2, origin 1). When it can prompt it resolves remotes via the API: 0 repos → `remotes[0]`, 1 → that repo, 2+ → error "please run `gh repo set-default`".
- **`gh repo set-default`.** At most one argument; must run inside a git repo. Argument parsed as `owner/repo` first, then as a remote name. No arg + no TTY → FlagError "repository required when not running interactively". No arg + TTY: one known repo is picked automatically (printing "Found only one known remote repo"), several open `Select("Which repository should be the default?")` with the current default preselected. It unsets the current default, then sets `base` on the matching remote (if none matches it writes `owner/repo` on the first remote — ado's spec forbids that). `-v/--view` prints the default on stdout, or a failure line on stderr when none — and returns nil (exit 0). `-u/--unset` prints messages only on a TTY, exit 0. Success line "✓ Set %s as the default repository for the current directory" only on a TTY. No `-R`.

**This codebase today**
- `internal/git` has no config helpers; commands call `f.GitClient.Exec(ctx, "config", ...)` (close.go handles `--get-regexp` exit 1 like gh). `git.Remote` has Name, FetchURL, PushURL.
- `ResolveBaseRepo(override, remotes func())`: -R > `ADO_REPO` > origin > upstream > first ADO remote; `NewFactory` wires it to `GitClient.Remotes`.
- `BaseRepoFromGit()` is `RepoOverride == "" && ADO_REPO == ""`. It needs no change: a pinned remote is still a remote of the checkout.
- `shared.MatchRemote`/`PointsAt` compare remotes to a Repo case-insensitively. `Prompter.Select` has no preselect. `gittest.Runner` treats unanswered `--get-regexp`/`--unset-all` as silent successes; `Mutations()` records non-`--get` config calls.

**Recommended fit**
1. **internal/git.** Add `Resolved string` to `Remote` and `(*Client).ResolvedRemotes(ctx)`: `Remotes`, then `Exec("config", "--get-regexp", `^remote\..*\.ado-resolved$`)` (exit 1 = none); parse with `TrimPrefix("remote.")`/`TrimSuffix(".ado-resolved")` so dotted remote names survive (gh's `SplitN(".", 3)` breaks them). 2. **ResolveBaseRepo.** Same signature; in the loop return an ADO remote with `Resolved == "base"` before origin/upstream; ignore other values; fall through if its URL is no longer ADO. Add table rows.
3. **Factory.** The `NewFactory` closure calls `ResolvedRemotes`; `BaseRepoFromGit` unchanged.
4. **`repo set-default`.** Load `ResolvedRemotes` once. Set: `git config --unset-all remote.<n>.ado-resolved` on every remote that has it, then plain `git config remote.<n>.ado-resolved base` (not `--add`, which can duplicate values so a later `--unset` fails with exit 5). `--unset`: `--unset-all` on every resolved remote. `--view`: print `org/project/repo`. Matching: remote name first, then `[[org/]project/]repo` or URL against parsed ADO remotes (o16), reusing `PointsAt`/`MatchRemote` ideally moved into adocontext. No arg + TTY: ADO remotes deduped by repo; zero → error, one → auto-pick, several → `Select`. No arg + no TTY → FlagError. `ErrNotGitRepo` → "must be run from inside a git repository". Use `--get-regexp`/`--unset-all`, not the `git config get`/`unset` subcommands (Git 2.46+). `git remote remove`/`rename` move or drop the key with the section, so no stale-key handling.
