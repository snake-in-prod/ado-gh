## Phase 1: PR State Changes (close, reopen, ready) — phase

### q1. Codebase reuse for pr close/reopen/ready: what api.PRClient, the PR finder, merge's confirmation/--yes/non-TTY pattern, the git client and create's body/editor input already provide; what is missing and where new helpers should live
**Answer:** Most of Phase 1 already exists. Two API methods, the local git steps and a small state guard are missing. No new package, abstraction or dependency is needed.

**Already there**
1. **api.PRClient** (`api/pr.go`):
   - `UpdatePullRequest(ctx, id, *git.GitPullRequest)` patches only non-nil fields. close = `Status=Abandoned`, reopen = `Status=Active`, ready = `IsDraft=&false`, `--undo` = `IsDraft=&true` (`IsDraft` is `*bool` with omitempty, so `&false` is still sent).
   - `CreateThread(ctx, id, content)` covers `-c/--comment`; `pr review` already uses it (review.go:116).
   - `Repository(ctx)` returns `DefaultBranch` as `refs/heads/x` (create and checkout use it). `RepositoryByID` exists. Errors are `*api.HTTPError` with `IsNotFound`.
2. **PR finder** (`pkg/cmd/pr/shared/finder.go`): `shared.Find(ctx, f, ref)` resolves number, `!n`, URL, branch or current branch, returns `(pr, *api.PRClient, repo, err)` and honours `-R`. For a branch it picks the newest active PR, else the newest of any status, so `reopen <branch>` finds the abandoned PR. `shared.PRURL`/`RepoURL` exist.
3. **Confirmation pattern** (`pkg/cmd/pr/merge/merge.go`):
   - Guard: `if !o.yes && !f.IOStreams.CanPrompt() { return cmdutil.FlagErrorf("--yes required when not running interactively") }` — the spec's exact message (spec FR3). As a FlagError it exits 1 and prints usage.
   - `f.Prompter.Confirm(q, true)`; decline → `cmdutil.CancelError` (exit 2). Flag `-y/--yes`. Success line on `ErrOut`, TTY only, green check.
   - merge has an inline state guard (merge.go:103-105), the only precedent.
4. **Git client** (`internal/git/git.go`): thin — `Exec`, `Remotes`, `CurrentBranch` (`ErrNotOnAnyBranch` on detached HEAD), `*git.Error` with exit code. Commands call `f.GitClient.Exec` with raw args inline (checkout.go:115-158, create.go:233-242). Tests swap `git.Client{Run: stub}`; `coGit` (checkout_test.go:25-47) records calls and fails unanswered `rev-parse`.
5. **Body/editor input**: only the unexported `readBody(f, path)` (`-F` file or `-` stdin, create.go:201-213). No `$EDITOR` support anywhere in the repo. Phase 1 needs neither (`-c` takes plain text); both belong to Phase 3.
6. **Other**: `CancelError` exits 2, any other error 1. No warning helper, but `ColorScheme().Yellow` exists. Fork detection: `pr.ForkSource != nil && pr.ForkSource.Repository != nil` (checkout.go:70). HTTP test harness to copy: merge_test.go:36-100. Commands are registered in pr.go:22-29.

**Missing**
1. **Remote branch delete** (`api/pr.go`). The SDK has `UpdateRefs` (POST, location `2d874a60-a811-4f62-9c9f-963a6ea0a55b`, returns `[]GitRefUpdateResult` with `Success`, `UpdateStatus`, `CustomMessage`) and `GetRefs` (same location; `Filter` is starts-with, so `heads/feat` matches `heads/feature`). Add:
   - `Ref(ctx, name) (*git.GitRef, error)` — nil when absent, exact match on `refs/heads/<b>`. It gives close a fresh `oldObjectId` (`LastMergeSourceCommit` is stale after later pushes), detects an already deleted branch, and is reopen's deleted-branch pre-check.
   - `DeleteRef(ctx, name, oldObjectID) error` — zero `newObjectId`; error when `Success` is false.
   - Add the refs location to `httpmock.GitPRLocations` (git.go:4-17). The route template `{project}/_apis/git/repositories/{repositoryId}/refs/{*filter}` comes from the REST layout, not the SDK; httpmock already handles catch-all `{*x}` templates (httpmock_test.go:134).
   - `merge -d` doesn't help: it uses server-side `CompletionOptions.DeleteSourceBranch` (merge.go:120-122), which doesn't apply to abandon.
2. **Local branch delete / switch to default branch**: nothing exists. Do it inline in close with `f.GitClient.Exec`: `rev-parse --verify --quiet refs/heads/<b>`; if `CurrentBranch == b`, `checkout <default>` (from `c.Repository(ctx).DefaultBranch`, `refs/heads/` trimmed); then `branch -D <b>`. `checkout <default>` only creates a missing local branch from the remote-tracking one when `checkout.guess` is on (default) and exactly one remote has it, so close must report a checkout failure instead of assuming success. Only close uses this, so no typed `internal/git` helper (extract later if Phase 2+ needs it).
3. **State helper** (new `pkg/cmd/pr/shared/state.go`), shared by close, reopen and ready, e.g. `SetState(ctx, ios, c, pr, update, comment) (changed bool, err error)`. Rules: completed → error (exit 1); already in target state → yellow `!` warning on `ErrOut`, exit 0; ready on a non-active PR → error. Then `CreateThread` if a comment was given, then `UpdatePullRequest`. Confirmation and `-d` stay in close. Move the thrice-copied `deref[T]` (list.go:181, merge.go:192, view.go:311) here.
4. **Commands**: one package each (`pkg/cmd/pr/close`, `reopen`, `ready`) with `options` + `NewCmdX` + `run` + `_test.go`, registered in pr.go.

Caveat: whether a rejected ref update comes back as HTTP 200 with `success:false` or as an HTTP error is not confirmed live; `DeleteRef` should handle both.

### q2. Azure DevOps REST semantics for PR state changes: abandon/reactivate, draft/publish via isDraft, deleting the remote source branch via a zero-newObjectId refs update (permissions, forks, az/web UI), and error responses to map
**Answer:** The core calls are documented; the server's error text for refused state changes is not. Check state on the client before calling the API instead of parsing server messages.

1. **Abandon / reactivate**: plain PATCH with `status` (`abandoned` / `active`) — `PRClient.UpdatePullRequest` already does it. az sets only `pr.status` for these. Completed PRs can't be reactivated (community source only; docs only describe reactivating from the Abandoned tab) → guard on the fetched `pr.Status` like merge.go:103. With a deleted source branch the web UI disables Reactivate (community report); the fix is to restore the branch (web "Restore branch" recreates it at its last commit, no retention limit) or push it again. No documented REST error exists, so `reopen` should pre-check: list refs `heads/<branch>` in the source repository (fork repo when `forkSource` is set), match exactly, and fail with "source branch X was deleted; push it (`git push origin X`) or restore it, then retry".
2. **Draft / publish**: `isDraft:false` publishes, `isDraft:true` converts back (what `az repos pr update --draft` does). `isDraft` is missing from the prose list of updatable fields on the 7.1 Update page but present in its request body schema. Voting doesn't block "Mark as draft": "Marking a PR as draft removes all existing votes." Drafts don't run build validation automatically, disable voting and don't add required reviewers; publishing "assigns required reviewers, evaluates policies, and kicks off voting". Drafting an abandoned/completed PR is undocumented → guard on the client (spec FR6). Sending `isDraft` alone (not with `status`) is a precaution, not a documented constraint — az sends both in one PATCH.
3. **Deleting the remote branch**: POST `.../git/repositories/{repoId}/refs` with `[{name:"refs/heads/X", oldObjectId:<current tip>, newObjectId:"0"*40}]` — SDK `UpdateRefs` (api-version 7.1-preview.1). Get `oldObjectId` from GetRefs at call time (a wrong value returns `staleOldObjectId`), as Microsoft's terraform provider does.
   - Response is 200 with one result per ref; check `Success`/`UpdateStatus` yourself (the SDK and az don't; terraform does).
   - Success: `succeeded`; `succeededNonExistentRef` (already gone → report already deleted); `succeededCorruptRef` (documented "only during deletes") also counts as success.
   - Failures: `writePermissionRequired` (SDK: "lacks write permissions required to write this ref"; most likely missing Force push — inference), `forcePushRequired`, `locked`, `rejectedByPolicy`, `rejectedByPlugin`, `staleOldObjectId`, `invalidRefName`.
   - Permissions: token scope `vso.code_write`; deleting a branch needs Force push. Contributors don't get it by default, but branch creators automatically get Contribute, Force push, Manage permissions and Remove others' locks — authors can usually delete their own branches, others usually get `writePermissionRequired`.
   - UI/az: the web UI deletes from the Branches page; PR completion has "Delete <branch> after merging" (`completionOptions.deleteSourceBranch`, used by `ado pr merge -d`). Abandon has no built-in delete, so `close -d` makes its own refs call. az's `az repos ref delete` sends a zero `newObjectId`; `object_id` is optional and, when omitted, az looks it up with `get_refs(filter=name)` and fails unless exactly one ref matches (the same starts-with problem).
   - Forks: the branch lives in `forkSource.repository` and would need Force push there → skip and warn (spec); fork detection exists (checkout.go:70).
   - Order: abandon first, then delete (gh order).
4. **Errors**: server errors arrive as `azuredevops.WrappedError` (`TypeKey`, `TypeName`, `ErrorCode`, `Message`); ado's `HTTPError` keeps only `StatusCode` and `Message`, and merge already matches on message text (merge.go:171-176). Map 401/203 → exit 4 (transport), 404 → not found, 403 → missing PR permission, 400 → pass the server message through, ref results with `Success == false` → `UpdateStatus` messages above. Don't hard-code TF error codes for "cannot edit in this state" or "source branch missing" — none could be confirmed.

## Phase 2: `ado pr edit` — phase

### q3. ADO APIs and SDK v7.1.0 support for pr edit: adding/promoting required reviewers, removing user and team reviewers, linking/unlinking work items, PR labels, and retargeting via targetRefName
**Answer:** Every edit works with the SDK as it stands, except promoting an existing optional reviewer to required, which goes through the add-reviewer PUT with undocumented vote behaviour. Work-item links have no PR-side endpoint and need a work item tracking client (none in the repo yet).

1. **Field edits (-t, -b, -F, -B)**: `PRClient.UpdatePullRequest` (api/pr.go:114) marshals pointer/omitempty fields, so only set fields are sent. The 7.1 docs allow Status, Title, Description (≤4000 characters), CompletionOptions, MergeOptions, AutoCompleteSetBy.Id and TargetRefName "when the PR retargeting feature is enabled"; anything else throws `InvalidArgumentValueException` or is silently ignored. So `-B` = `TargetRefName: "refs/heads/<base>"`, and reviewers/labels/work items can't go in the PATCH. Where retargeting is off, expect an exception or a silent no-op → check the response's `TargetRefName`. Behaviour after a retarget with conflicts is undocumented: the PR stays active and `mergeStatus` updates asynchronously. Guard locally that the branch exists and isn't the source branch.
2. **Add a required reviewer**: `git.CreatePullRequestReviewer` — `PUT .../reviewers/{reviewerId}` with `IdentityRefWithVote{IsRequired: true}`, `Vote` unset. The batch `CreatePullRequestReviewers` used by `PRClient.AddReviewers` (api/pr.go:128) takes `[]webapi.IdentityRef` in the Go SDK, which has no `IsRequired` (az's batch call sends `IdentityRefWithVote` with `is_required=True`, so the wire format may accept it — another informal sign the server honours the flag). `UpdatePullRequestReviewer` only patches isFlagged/hasDeclined; `UpdatePullRequestReviewers` "does not support updating required reviewers". No Microsoft source documents PUT with `isRequired:true`; Renovate has sent it since v32.228.0 (2022-10). Against it: node-api issue #333 (2019) saw it ignored, Microsoft's MCP maintainer said (2026-02) the add path has no IsRequired, and the Learn page's CLI tab says to change optional/required "in the browser". Live verification is mandatory.
3. **Promote an existing optional reviewer**: the same PUT. Look the reviewer up in `pr.Reviewers` first to report "promoted" vs "added" (view.go:250 already reads `IsRequired`). Whether it keeps an existing vote is undocumented; leave `Vote` out (the API says vote must be zero when adding others).
4. **Remove user/team reviewers**: `git.DeletePullRequestReviewer` (DELETE, 200). Teams by identity GUID, as `IdentityResolver` returns. Reviewers required by branch policy can't be removed → partial failure. Check `pr.Reviewers` first so "not a reviewer" is a local warning.
5. **Work items**: no PR-side write API (`GetPullRequestWorkItemRefs` is read-only; `workItemRefs` only works on create, create.go:161-169).
   - Link: `workitemtracking.UpdateWorkItem` (json-patch) with `{op: add, path: /relations/-, value: {rel: "ArtifactLink", url: "vstfs:///Git/PullRequestId/{projectGUID}%2F{repoGUID}%2F{prId}", attributes: {name: "Pull Request"}}}`. GUIDs from `pr.Repository.Project.Id` / `pr.Repository.Id` (as view.go:123-126). "Relation already exists." = success.
   - Unlink: `GetWorkItem` with `Expand=Relations`, find the first relation whose URL matches (case-insensitive — an improvement over az, which compares exactly and, lacking a `break`, picks the wrong index on duplicates), then patch `[{op: test, path: /rev, value: rev}, {op: remove, path: /relations/{index}}]`.
   - Unlinking removes only the PR link; branch/commit links stay.
6. **Labels**: `git.CreatePullRequestLabel` with `core.WebApiCreateTagRequestData{Name}` creates the tag if missing; `git.DeletePullRequestLabels` (`LabelIdOrName`) removes it from the PR without deleting the tag. Use `GetPullRequestLabels` / `GitPullRequest.Labels` for "label not found" warnings and interactive prefill. PR and work item tags share a 150,000-per-organization pool.

### q4. ADO PR threads/comments APIs and SDK functions: replies, edit/delete, thread status, inline threads (filePath, line/offset, iteration context, changeTrackingId), identifying the signed-in user's comments, and recognizing system threads
**Answer:** Everything is in SDK v7.1.0 (git package); no new dependency or raw REST call. Most calls use 7.1-preview.1; `GetPullRequestIterations` uses 7.1-preview.2.

1. **Reply**: `CreateComment(ctx, CreateCommentArgs{Comment, RepositoryId, PullRequestId, ThreadId, Project})` (POST `.../threads/{threadId}/comments`) with `Comment{Content, CommentType: Text, ParentCommentId}`. `parentCommentId` is optional (Microsoft's MCP omits it; the doc sample sends 1, the root comment); set it to the thread's first comment ID, as the web UI does. Max 500 comments per thread.
2. **Thread status**: `UpdateThread` (PATCH) with only `Status`. Values `active, fixed, wontFix, closed, byDesign, pending` (plus `unknown`) — exactly the spec's `--status` set; map input case-insensitively and reject others. `--thread N --status S -b body` = two calls (CreateComment, then UpdateThread).
3. **Edit / delete**: `UpdateComment` (PATCH, `{ThreadId, CommentId, Comment{Content}}`) and `DeleteComment` (DELETE). Deletion is soft: the comment stays with `isDeleted: true` and no content; a thread with all comments deleted gets `isDeleted: true`. The current `view.threads` filter already drops both.
4. **Inline thread**: `CreateThread` with `Comments`, `Status: Active`, `ThreadContext` and `PullRequestThreadContext`.

Use start offset 1. The samples use start `{5,1}` and end `{5,13}` (end offset past the first character); any end offset renders on the end line.
   - `--side right` (default): `RightFileStart`/`RightFileEnd` (source/new file). `--side left`: `LeftFileStart`/`LeftFileEnd` (target/base file; for deleted lines). Set one side only.
   - `PullRequestThreadContext`: docs say `changeTrackingId` "Must be set for pull requests with iteration support"; the API accepts threads without it but they aren't tracked across pushes. ## Phase 4: `ado pr diff` — phase

### q6. Producing a unified diff that matches the web Files tab: fetching SHAs vs branches in a clone, merge-base vs commonRefCommit, refs/pull/{id}/merge; API fallback via iteration changes, blobs, binary detection and rate/size limits
**Answer:** The Files tab is a three-dot diff from the latest iteration's `commonRefCommit` to its `sourceRefCommit`. Both paths should take those SHAs from the API.

1. **Clone path**:
   - Fetch the PR's source and target refs from the matching ADO remote (branch tips are always advertised). Reuse the remote matching/refspec code (checkout.go:93-96, 122) and, for forks without a remote, the fetch-by-URL path (checkout.go:136-142).
   - Fetching a bare SHA works on Azure Repos in practice (the Pipelines agent fetches `+<sha>:refs/remotes/origin/<sha>`; GitHub refuses it, agent PR #2283), but no doc says Azure Repos allows reachable-SHA wants → fallback only.
   - Diff `git diff <commonRefCommit> <sourceRefCommit>` from the latest iteration (GET `.../iterations`, highest id). Check with `git cat-file -e <sha>^{commit}`; if missing, try `git fetch <remote> <sha>`, then fall back to `git merge-base <target> <source>`.
   - Plain merge-base usually agrees but can differ on criss-cross merges or when the target has merged part of the source. Unverified: if ADO doesn't refresh `commonRefCommit` when only the target moves (iterations come from source pushes), the iteration base and the Files tab could differ for a while — check once against a real PR.
   - `--name-only`/`--patch` use the same range.
   - `refs/pull/{id}/merge` is not needed and not always available (missing/stale on conflicts or while merging); `merge^1..merge` isn't the Files tab either. No head ref exists (checkout.go:30).
2. **API path**:
   - Changes: GET `.../iterations/{latest}/changes`; default `$compareTo` 0 = common commit = Files tab. `$top` default 100, max 2000; loop `$top=2000`, `$skip=nextSkip` until `nextTop`/`nextSkip` are 0 (SDK `*int`, nil = 0). The SDK has `GetPullRequestIterationChanges` and `GetPullRequestIterations`.
   - `changeType` is a flags value (UI shows "rename, edit") → split on comma, trim, test membership. `originalPath` only when the path changed. `item` is `interface{}`: decode `objectId`, `originalObjectId`, `path`.
   - Headers: add → `new file mode` + `--- /dev/null`; delete → `deleted file mode` + `+++ /dev/null`; rename → `rename from/to` plus hunks if `edit`. Strip ADO's leading `/` for `a/`/`b/`. The rename threshold is git's default, but ADO's server-side pairing may still differ from local git in edge cases (copies, several candidates) — tests must not require identical rename output across paths.
   - Content: `GetBlobContent` (octet-stream) for `objectId` and `originalObjectId`. Microsoft shows `originalObjectId` only in the `$compareTo` example; a third-party MCP reads it with the default compareTo, but presence isn't guaranteed → fall back to `GetItemContent` with path (or originalPath) and `versionDescriptor {version: commonRefCommit, versionType: commit}`.
   - Forks: request new-side blobs with `forkSource.repository.id` (reading them via the target repo is undocumented; docs say forks are isolated).
   - Binary: git's rule — NUL byte in the first 8000 bytes → `Binary files a/x and b/x differ` (`/dev/null` on add/delete). Skip `contentMetadata.isBinary` (extra request).
3. **Limits**:
   - Requests: about 2 per changed file + 1 for iterations + ceil(N/2000) for change pages.
   - Throttling: 200 TSTUs per sliding 5 minutes; delays up to 30 s, 429 when blocked. `Retry-After` can also arrive on HTTP 200 responses, and `X-RateLimit-*` headers appear before delays start — a client should also slow down on a 200 carrying `Retry-After` or `X-RateLimit-Remaining=0`. The codebase has no 429/Retry-After handling (api/http_client.go).

**Libraries** (Go module proxy, 2026-10-11):

**Speed**: the cap keeps it near linear; `toUnified` does one `strings.Count` per edit (unified.go:124-127) — fine for normal files. Optionally treat very large blobs like binaries.

**Headers to write** (checked against real git):
- Every file: `diff --git a/<old> b/<new>` (never `/dev/null` here).
- Added: `new file mode 100644`, `index 0000000..<new7>`, `--- /dev/null`, `+++ b/x`. Deleted: `deleted file mode 100644`, `index <old7>..0000000`, `--- a/x`, `+++ /dev/null`.
- Renamed: `rename from`/`rename to`, then `index <old7>..<new7> 100644` and `---`/`+++`; content-unchanged renames end after `rename to`. `git apply` accepts a rename without `similarity index` (checked), so omit it (ADO has no value).
- Binary: `Binary files a/x and b/x differ` (`/dev/null` side on add/delete); NUL in the first 8000 bytes.
- `index`: `originalObjectId`/`objectId` cut to 7 chars (git uses `core.abbrev` and may print more when 7 is ambiguous — fine for generated output); mode always 100644 (ADO exposes no modes).
- Empty added file: go-udiff returns "" → header writer still prints `diff --git`, `new file mode`, `index`.

**Colour**: `pkg/iostreams` already applies `NO_COLOR`/`CLICOLOR=0`/`CLICOLOR_FORCE` via go-gh (iostreams.go:49). `--color` like gh: `auto` → `IO.ColorEnabled()`, `always` → true, `never` → false. gh's colorizer: header lines (`diff`, `index`, `---`, `+++`, checked before `+`/`-`) `\x1b[1;37m`, `+` `\x1b[32m`, `-` `\x1b[31m`, reset `\x1b[m`, `@@` uncoloured. **`--patch`**: `git format-patch --stdout <target>..<source>` (mbox, one message per commit; merge commits omitted); gh colours it with the same colorizer. Clone diff can be `git diff --no-color --no-ext-diff <target>...<source>` (three dots = from merge base); `--name-only` adds `--name-only` and disables `--patch` (gh).
