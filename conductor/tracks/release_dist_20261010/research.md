**3. Alias and extension dispatch**

## Phase 1: Build Metadata, `ado version`, Update Notifier — Build info (`internal/build`)

### q2. In Go 1.25–1.27, what does runtime/debug.ReadBuildInfo report for a binary built with `go install module/cmd/x@vX.Y.Z` (Main.Version, pseudo-versions, `(devel)`), and when are the `vcs.revision`, `vcs.time`, `vcs.modified` settings present or absent (module-proxy builds vs local checkout builds, `-trimpath`, `-buildvcs=auto/false`, GoReleaser builds)? Recommend the fallback logic for Version/Commit/Date/Dirty when ldflags are empty.
**Answer:**

`setBuildInfo` (`cmd/go/internal/load/pkg.go`) is identical across release-branch.go1.25, go1.26 and go1.27 (only a new `*modfetch.Fetcher` parameter and a typo fix); the 1.26/1.27 release notes list no build-info changes. Since Go 1.24, `go build` also stamps `Main.Version` from git.

| Build | `Main.Version` | `Main.Sum` | `vcs.*` settings |
|---|---|---|---|
| `go install mod/cmd/ado@v1.2.3` (proxy or direct) | `v1.2.3` | `h1:…` | **absent** — module-cache build, `p.Module.Version != ""` skips the VCS block |
| `go install …@main`/`@<sha>`/untagged `@latest` | pseudo-version `vX.Y.(Z+1)-0.<ts>-<12hex>` or `v0.0.0-<ts>-<12hex>` | `h1:…` | absent; commit and UTC time only inside the pseudo-version |
| `go build`/`go install` in a git checkout, `-buildvcs=auto` | Go 1.24+: tag, or pseudo-version after a tag, plus `+dirty`; `(devel)` if the repo lookup fails or the repo root has no `go.mod` | empty | **present**: `vcs=git`, 40-char `vcs.revision`, `vcs.time` (RFC3339, UTC), `vcs.modified`. **Untracked, non-ignored files count as modified** (`git status --porcelain`) |
| same with `-buildvcs=false` | `(devel)` | empty | absent |
| same with `-trimpath` | unaffected | – | still present; `-trimpath` only drops `-ldflags`/CGO flags from build info and adds `-trimpath=true` |
| repo with no commits | `(devel)` | – | `vcs=git` and `vcs.modified=true` only |
| main package and cwd in different repos, or no `git` (auto) | `(devel)` | – | silently omitted |
| `go run` | `(devel)` | – | absent (only build/install pass `AutoVCS: true`) |
| `go test` binaries | not the real version | – | absent (`IsTestOnly`) |
| GoReleaser, default `dir: .` | tag | – | present (it runs `go build` in the checkout; needs `fetch-depth: 0`). With `gomod.proxy: true` it builds from the module cache: tag version, no `vcs.*`, Dirty always false |

**Recommended fallback for `internal/build`:**
```go
var Version, Commit, Date = "", "", "" // -X internal/build.*
var Dirty bool
var readBuildInfo = debug.ReadBuildInfo // test seam

func init() {
	bi, ok := readBuildInfo(); if !ok { if Version == "" { Version = "DEV" }; return }
	s := map[string]string{}; for _, kv := range bi.Settings { s[kv.Key] = kv.Value }
	_, local := s["vcs"]
	if Version == "" {
		if v := bi.Main.Version; v != "" && v != "(devel)" && !local { Version = strings.TrimPrefix(v, "v") } else { Version = "DEV" }
	}
	if Commit == "" { Commit = s["vcs.revision"] }
	if Date == "" { Date = s["vcs.time"] }
	Dirty = s["vcs.modified"] == "true"
}
```
- **Version:** ldflags; else `Main.Version` (without `v`) only when it is a real version and no `vcs` setting exists (module-cache install); everything else `DEV`. This keeps the spec's "Local builds report DEV" even though Go 1.24+ stamps local builds.
- **Commit/Date:** ldflags, then `vcs.revision`/`vcs.time`. Empty for `go install` builds, so `ado version` omits the commit line or shows `unknown`. Optionally parse the pseudo-version with `-(\d{14})-([0-9a-f]{12})$` (o4); do not add `golang.org/x/mod/module` for it.
- **Dirty:** no ldflag; always read `vcs.modified`; optionally also a `+dirty` suffix on `Main.Version`.
- **GoReleaser ldflags:** `-X …/internal/build.Version={{.Version}} -X …Commit={{.FullCommit}} -X …Date={{.CommitDate}}`. `.Date` is build time (breaks reproducibility); `.Commit` is deprecated. Trim `v` defensively.
- Today the version is only `var version = "DEV"` (`cmd/ado/main.go:19-20`) feeding cobra's `Version` and the User-Agent, so `internal/build` replaces it in one place.

Verification notes: GoReleaser runs its git dirty check (`git.Pipe`) **before** the global before-hooks, so files written by hooks (manpages, completions) do not fail GoReleaser's dirty check — they only make binaries report `vcs.modified=true`. Gitignoring hook output is still needed for that reason. The pgsty/mc PR source was dropped as unverified.

## Phase 1: Build Metadata, `ado version`, Update Notifier — Install-method detection

### q3. How should `ado` detect how it was installed from os.Executable() (after EvalSymlinks) on each OS: Homebrew cask (Caskroom paths on macOS Intel /usr/local and Apple Silicon /opt/homebrew, Linuxbrew /home/linuxbrew/.linuxbrew; does a cask binary path resolve into Caskroom?), Scoop (`~/scoop/apps/<app>/current` and shims, global scoop), winget portable installs (`%LOCALAPPDATA%\Microsoft\WinGet\Packages\<Id>_<source-hash>\` and `WinGet\Links`), `go install` (GOBIN, GOPATH/bin), the install-script default dir (~/.local/bin, %LocalAppData%\Programs\ado). How does GitHub's gh CLI implement this (isUnderHomebrew, etc.) and what upgrade commands does it print? Note any existing path helpers in this repo.
**Answer:**

Write one pure function `detectInstallMethod(exe, goos, getenv, *debug.BuildInfo)`. Call `filepath.EvalSymlinks(os.Executable())` once outside it (raw path on failure). Normalize before matching — replace `\` with `/` and lowercase (`filepath.ToSlash` leaves backslashes alone on Linux) — so a Windows-path table runs on Linux CI. Inject `goos`/`getenv` like `config.dataDir(goos)`. Do not call `brew`.

First match wins:
1. **go install** — decide from build info, not the path: `bi.Main.Sum != ""` means `go install mod@version`; local and GoReleaser builds have an empty `Sum`. Checked with `go version -m`: gopls from `go install` shows `v0.16.2 h1:K1z0…`; this repo's `bin/ado.exe` shows a `+dirty` pseudo-version with no checksum. Covers custom `GOBIN`, `GOPATH/bin` and `~/go/bin` with no path rules. Guard: check the ldflags `internal/build` values first (release builds have them) and keep GoReleaser's `gomod.proxy` off, since a proxy-built release binary would also carry a checksum. Upgrade: `go install github.com/snake-in-prod/ado-gh/cmd/ado@latest` (from `bi.Path`).
2. **Homebrew cask** — the `binary` stanza symlinks `$(brew --prefix)/bin/ado` into `$(brew --caskroom)/ado/<version>/…`; after EvalSymlinks the path is in the Caskroom. Match the segment `/caskroom/ado/` anywhere (covers `/opt/homebrew`, `/usr/local`, `/home/linuxbrew/.linuxbrew`, custom prefixes; don't assume depth). Casks with binaries work on Linux since Homebrew 4.5.0. Message: `brew upgrade --cask ado`. No Cellar rule needed (we publish no formula; o6).
3. **Scoop** — the shim (`~\scoop\shims\ado.exe`, a copy of `shim.exe` plus `ado.shim`) starts `<root>\apps\ado\current\ado.exe` as a child, so `os.Executable` is already the real path (Scoop runs `link_current` before `create_shims`). `current` is a junction; since Go 1.23 EvalSymlinks on Windows does not follow mount points (`winsymlink=1`; go.mod is 1.25.8), so `current` normally stays. Match `/apps/ado/current/` (any root) or `/scoop/apps/ado/`. Global root defaults to `%ProgramData%\scoop` → `scoop update ado --global`, else `scoop update ado`.
4. **winget portable** — user scope `%LOCALAPPDATA%\Microsoft\WinGet\Packages\<Id>_<SourceId>\…`, machine scope `%ProgramFiles%\WinGet\Packages\…` (x86 packages under `ProgramFiles(x86)`). Folder name is `MakeSuitablePathPart(packageId + "_" + source)`. The PATH entry is a real symlink in `…\WinGet\Links` (machine: `%ProgramFiles%\WinGet\Links`), which EvalSymlinks resolves; if symlink creation fails winget adds the package dir to PATH. Match `/winget/packages/<lowercased id>_`, fallback `/winget/links/`. A custom `portablePackageUserRoot` falls back to the release URL. Message: `winget upgrade --id <Owner>.Ado`.
5. **Install script** — exe directly in `$HOME/.local/bin/` or `%LocalAppData%\Programs\ado\` (via injected `getenv`): print the re-run one-liner. Custom `--bin-dir` falls back to the release URL.
6. **Anything else** (incl. `.deb`/`.rpm` in `/usr/bin`): release URL.

**gh (v2.102.0, `internal/ghcmd/cmd.go`):** `executable()` deliberately returns the PATH symlink (`/usr/local/bin/gh`); `isUnderHomebrew()` runs `brew --prefix` and checks `<prefix>/bin/` prefix; Homebrew is the only detected method ("To upgrade, run: brew upgrade gh"), everyone else gets the release URL; Homebrew notices are held back while the release is < 24 h old (`isRecentRelease`); `ShouldCheckForUpdate` disables on `GH_NO_UPDATE_NOTIFIER`, `CODESPACES`, CI, non-TTY. Don't copy the `brew --prefix` subprocess.

**Existing helpers:** `pkg/cmdutil/factory.go:61` stores `os.Executable` unresolved in `f.Executable` (passed to extensions as `ADO_EXECUTABLE`, `pkg/extension/run.go:155` — don't change it); `internal/config/config.go:63` `dataDir(goos)` is the injection pattern; `pkg/cmd/alias/shared/shell.go:86-101` already knows Scoop's `apps\<app>\current` layout. No install-method helper exists.

Verification notes: the winget Links source is `src/AppInstallerCommonCore/Runtime.cpp` (lines 223-234), not AppInstallerSharedLib; `bin/ado` and `bin/ado.exe` were built with go1.27.2 and gopls with go1.23.1 (conclusion unchanged); spec FR2 (line 28) says "detected from the executable path", so using BuildInfo for go install needs a spec rewording.

**Answer:**

**gh's notifier (cli/cli trunk, v2.102.0)**
- `internal/ghcmd/cmd.go:135-145` starts the check before the command: `context.WithCancel`, unbuffered channel, goroutine calling `checkForUpdate`; errors print `warning: checking for update failed` only in debug.
- After `ExecuteContextC`, success path only (`cmd.go:242-258`): `updateCancel()` then `<-updateMessageChan`; if newer, stderr gets `A new release of gh is available: X → Y`, plus `brew upgrade gh` for Homebrew, plus the release URL. Homebrew notices are held back < 24 h (`isRecentRelease`, `cmd.go:246,329-331`).
- No explicit network timeout: the request is cancelled when the command ends, so it never delays a command; a very short command usually aborts an in-flight fetch (when `state.yml` is fresh there is no fetch to abort).
- Error paths (`cmd.go:187-240`) and `root.HasFailed()` (`cmd.go:239-241`) return before the channel is read: no notice on failure.

**`CheckForUpdate` (`internal/update/update.go:93-114`)**: reads `state.yml` (`checked_for_update_at`, `latest_release{tag_name, html_url, published_at}`); < 24 h old → no network. Notifies only when `versionGreaterThan` (hashicorp/go-version; `git describe` suffixes mapped to `-pre.0`).

**When gh skips:** `ShouldCheckForUpdate` (`update.go:82-90`): `GH_NO_UPDATE_NOTIFIER`, `CODESPACES`, `ci.IsCI()`, or stdout/stderr not a terminal. `ci.IsCI` is `CI || BUILD_NUMBER || RUN_ID` — no `TF_BUILD`. No subcommand is excluded by name; completion is covered by the TTY check. The notifier is compiled in only with the `updateable` build tag (PR #11024), set only by the Homebrew formula. Extensions have a separate notifier.

**CI variables:** GitHub Actions sets `CI=true` and `GITHUB_ACTIONS=true`. Azure Pipelines documents `TF_BUILD` and no `CI`, so check `TF_BUILD` explicitly. `BUILD_NUMBER` covers Jenkins/TeamCity, `RUN_ID` TaskCluster. **State file:** XDG Base Directory 0.8: `$XDG_STATE_HOME`, default `$HOME/.local/state`. go-gh v2.16.2 (`go.mod:11`) `StateDir()`: `XDG_STATE_HOME/gh`, then `%LocalAppData%\GitHub CLI` on Windows, then `~/.local/state/gh` (also macOS). **GitHub API:** `/releases/latest` returns "the most recent non-prerelease, non-draft release"; "Drafts and prereleases cannot be set as latest", so `-rc.N` never comes back and "stable only" needs no filter. Unauthenticated limit: 60 requests/hour per IP (`x-ratelimit-remaining`/`-reset`); 403/429 when exceeded. At one call per 24 h this is fine, but gh-style retry-on-failure would retry every command behind a rate-limited shared NAT (o7).

**`golang.org/x/mod/semver` (v0.41.0 in the module cache, not in go.mod):** requires a leading `v`; `Compare` returns -1/0/+1; invalid strings sort below valid ones and equal to each other; prereleases per SemVer 2.0.0 (`1.0.0-rc.1 < 1.0.0`, `rc.2 < rc.10`), build metadata ignored. **Reuse in ado:** hook into `run()` (`cmd/ado/main.go:29-35`); decide debug printing at read time (`f.Debug` final after parsing; `ADO_DEBUG` read in `factory.go:68`); TTY via `IsStdoutTTY`/`IsStderrTTY` (note `ADO_FORCE_TTY`); `ADO_EXTENSION_NAME` at `run.go:154`. **1. cobra/doc in v1.10.2 (`go.mod:15`)**

### q10. Can this repo produce bit-for-bit reproducible linux binaries from GoReleaser snapshot builds? **Already in place:** no cgo dependencies (go-keyring, wincred, godbus, atotto/clipboard are pure Go), no `replace`, no go.work, so `CGO_ENABLED=0` works ("Disabling cgo removes the host C toolchain as a relevant input"). **What breaks it if left alone**
1. **Date in ldflags** — GoReleaser's default injects `{{.Date}}` (current time); use `{{ .CommitDate }}`. Under `-trimpath` the `-ldflags` string is **not** recorded in build info (Go only records it when trimpath is off, go.dev/issue/52372), but the `-X` value still lands in the binary's data, so the switch is still required.
2. **Build paths** — without `-trimpath` the checkout path is embedded.
3. **VCS stamping** — `-buildvcs=auto` stamps `vcs.revision`, `vcs.time`, `vcs.modified`, and since Go 1.24 a main-module version with `+dirty`; "dirty" comes from `git status --porcelain`, including untracked files. Two builds would still match each other, but non-ignored hook output (manpages, completions) makes every release binary report dirty, breaking FR1's `dirty`. Keep `-buildvcs` on and gitignore `/manpages/`, `/completions/`.
4. **Toolchain drift** — `go.mod:3` is `go 1.25.8` with no `toolchain` line; `ci.yml:18,37` use `go-version: stable`. With `GOTOOLCHAIN=auto` a newer local toolchain is used, so releases are built with whatever `stable` is that day — not reproducible by others. setup-go v6+ `go-version-file` reads `toolchain`, else `go`. A `toolchain` line doesn't affect `go install m@v` users, but the target module's `go` line can still trigger a toolchain switch there — another reason to keep `go 1.25.8` as the minimum and add a separate `toolchain` line.

- Temp dir: `tmp=$(mktemp -d)`, `trap 'rm -rf "$tmp"' EXIT` **and** `trap 'exit 130' INT TERM HUP` — dash doesn't run the EXIT trap on SIGTERM otherwise (verified). With a foreground child, dash runs the trap only after that child exits (cleanup delayed, not skipped) — relevant for the harness's signal test.
- OS (`uname -s`): `Linux`→linux, `Darwin`→darwin; `MINGW*|MSYS*|CYGWIN*|Windows_NT` → windows zip or a pointer to install.ps1 (o29); else error.
- Arch (`uname -m`): `x86_64|amd64|x64`→amd64, `aarch64|arm64`→arm64; on Darwin x86_64 check `sysctl hw.optional.arm64` for `: 1` (Rosetta). No 32-bit-userland check (static binaries — inference).
- Checksum: `sha256sum`, then `shasum -a 256`, then `openssl dgst -sha256`; look up the exact file name in `checksums.txt` with awk and compare; avoid GNU-only `--ignore-missing`.
- Download: curl `--proto '=https' --tlsv1.2 -fsSL`, fallback wget `--https-only`; a base-URL override (e.g. `ADO_INSTALL_BASE_URL`) for tests, https-only flags only for the default GitHub URL.
- `mkdir -p` the bin dir, install with mode 755, print a PATH hint when `case ":$PATH:" in *":$bin_dir:"*` fails. `local` is non-POSIX (SC3043) but accepted by dash/bash/ksh/busybox — prefer prefixed globals or accept SC3043.

**install.ps1 (Windows PowerShell 5.1)**
- Always `-UseBasicParsing`: since the CVE-2025-54100 update (2025-12-09), PS 5.1 `Invoke-WebRequest` otherwise shows an interactive "Script Execution Risk" prompt that would hang `irm | iex`.
- `$ProgressPreference = 'SilentlyContinue'` around downloads and `Expand-Archive` (one report: ~20 s → 0.45 s). Bun's `curl.exe` path is optional.
- TLS: don't hard-code versions on .NET 4.7+ (`SystemDefault`); only OR in Tls12 when not `SystemDefault`: `if ([Net.ServicePointManager]::SecurityProtocol -ne 'SystemDefault') { [Net.ServicePointManager]::SecurityProtocol = [Net.ServicePointManager]::SecurityProtocol -bor 'Tls12' }`. This machine reports `SystemDefault` (.NET Release 533509).
- `Get-FileHash -Algorithm SHA256` and `Expand-Archive` (1.0.1.0, `.zip` only) are built in; `-eq` is case-insensitive for hex.
- Arch: `$env:PROCESSOR_ARCHITECTURE` is per process (x64 PowerShell on ARM64 sees AMD64); read the machine value from `HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Environment` like Bun.
- User PATH: not `[Environment]::SetEnvironmentVariable('Path', ..., 'User')` (expands `%USERPROFILE%` entries; pixi PR 692, Bun). Read `HKCU:\Environment` Path with `GetValue('Path', $null, 'DoNotExpandEnvironmentNames')`, append if missing, write back with `SetValue` keeping `ExpandString` when it contains `%`, broadcast `WM_SETTINGCHANGE` via `SendMessageTimeout` (Bun's `Publish-Env`), and update `$env:PATH` for the session.
- `irm url | iex` can't pass `-Version`/`-BinDir`: support env vars too (like `UV_INSTALL_DIR`) or document `& ([scriptblock]::Create((irm url))) -Version x` (o30). Wrap the body in a function called at the end.

### q18. Token requirements for GoReleaser publishing: can a fine-grained PAT push to owner/homebrew-tap and owner/scoop-bucket and open a pull request from owner/winget-pkgs fork into microsoft/winget-pkgs (cross-owner PRs), or is a classic PAT with public_repo required (what GoReleaser docs and winget community recommend in 2026)? Best practices for a GPG signing key used in CI (subkey, passphrase, import via crazy-max/ghaction-import-gpg vs gpg --batch, cleanup), and publishing to keys.openpgp.org.
**Answer:**

No single fine-grained PAT can do all of it. It can push to `<owner>/homebrew-tap`, `<owner>/scoop-bucket` and the `<owner>/winget-pkgs` fork, but not open the PR into microsoft/winget-pkgs; that needs a classic PAT with `public_repo`.

**1. Tokens**
- GoReleaser opens the PR with `PullRequests.Create(ctx, base.Owner, base.Name, …)` and `Head: headString(base, head)` (`internal/client/github.go:315`, v2.18.3) — a POST to `/repos/microsoft/winget-pkgs/pulls`, a write on a public repo the token owner neither owns nor belongs to.
- GitHub lists "contribute to public repos where the user is not a member" as a fine-grained PAT gap and says "Only personal access tokens (classic) have write access for public repositories that are not owned by you". Community #106661 (TBBle's reply): opening a PR needs a token whose resource owner is the target, which you can't create unless you own it or are an org member.
- winget-releaser requires a classic PAT with `public_repo` (+ `workflow`) — "New fine-grained PATs aren't supported". GoReleaser's docs only say "This might require a personal access token" and the Actions guide asks for "a custom Personal Access Token with `repo` permissions". `GITHUB_TOKEN` is limited to its own repo.
- GoReleaser v2.18 adds `repository.pull_request.token` (`repository.md:51-55`): the winget pipe uses `repository.token` for fork sync and pushes (`winget.go:461`) and `pull_request.token` only to open the PR (`winget.go:500`). Least-privilege split:
  - `PACKAGES_PAT` (fine-grained): owner `<owner>`, repos homebrew-tap, scoop-bucket, winget-pkgs fork; Contents read/write (+ Metadata read); optionally Workflows read/write on the fork for merge-upstream (microsoft/winget-pkgs has `.github/workflows`).
  - `WINGET_PR_PAT` (classic): `public_repo` only, as `winget.repository.pull_request.token`.
  - Fallback: one classic `public_repo` (+ `workflow`) PAT for everything (writes to every public repo the account can access).
- A failed fork sync is only a warning (`winget.go:476`). The docs say a failed PR "will not fail the pipeline", but in v2.18.3 `OpenPullRequest` (`github.go:315`, only 422 is warned) returns other errors, which the pipe passes up (`winget.go:509`) — a 403 surfaces as a publish error.
- The PR-token account signs the Microsoft CLA once. If `<owner>` is an org, the fine-grained PAT's resource owner is the org (may need approval). Expiry reminders on both tokens.

**2. GPG in CI**
- Key layout: dedicated release identity; certify-only primary kept offline with an offline revocation certificate; a signing subkey with 1–2-year expiry is the only CI secret, exported with `gpg --armor --export-secret-subkeys <SUBKEY_FPR>!` ("each followed with an exclamation mark"); keep a passphrase as `GPG_PASSPHRASE`; publish the full public key and fingerprint in the README.
- Recommended import: **crazy-max/ghaction-import-gpg v7.0.0** (`2dc316deee8e90f13e1a351ab510b4d5bc0c82cd`, node24, pin by SHA). GoReleaser's Actions guide documents this pairing (its example uses v6) with `GPG_FINGERPRINT: ${{ steps.import_gpg.outputs.fingerprint }}`. Inputs `gpg_private_key`, `passphrase`, `fingerprint` ("Specific fingerprint to use (subkey)"); with `fingerprint` the passphrase is preset only for that subkey's keygrip (`src/main.ts` ~54-80), so GoReleaser's `gpg --detach-sig` runs without a TTY. `action.yml` declares `post: dist/index.js`; its cleanup runs `gpg --batch --yes --delete-secret-keys` on the primary fingerprint saved in state and kills the agent (`src/main.ts:135-154`) — covers the spec's cleanup with no extra step. `.goreleaser.yaml`: `signs: [{artifacts: checksum, args: ["-u","{{ .Env.GPG_FINGERPRINT }}","--output","${signature}","--detach-sign","${artifact}"]}]`.
- Alternative without a third-party action: `GNUPGHOME=$RUNNER_TEMP/gnupg`, `gpg --batch --import`, sign with `--batch --pinentry-mode loopback --passphrase-fd 0` (GoReleaser `stdin: "{{ .Env.GPG_PASSPHRASE }}"`), plus an `if: always()` step `gpgconf --kill gpg-agent; rm -rf "$GNUPGHOME"`. The GnuPG manual: since 2.0 the passphrase "is only used if the option --batch has also been given", since 2.1 "--pinentry-mode also needs to be set to `loopback`".
- **keys.openpgp.org:** upload through the `/upload` web form (or the VKS API `POST /vks/v1/upload` then request-verify; `/pks/add` and `gpg --send-keys` don't trigger email verification), then verify the email. Without verified identity the key is served but "GnuPG considers keys that contain no identity information to be invalid, and refuses to import them". Also ship the key file (KEYS or a docs page) and fingerprint in the README.
